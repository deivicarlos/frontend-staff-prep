Track 1 · What changed, 2024–2026

Q1 · What changed

React Compiler reached v1.0 in October 2025. What does it actually do?

Automatic memoisation. The compiler analyses your components at build time and inserts the memoisation you used to hand-write. The practical consequence is large: useMemo, useCallback and React.memo stop being the performance toolkit they were in 2024. If your instinct is still "wrap it in useCallback," that instinct is now dated. react.dev — React Compiler
Q2 · What changed

React 19 introduced use(). What can it do that no hook can?

It breaks the rules of hooks, on purpose. use() reads a promise or a context and can sit inside an if or a loop, because it isn't tied to the positional hook slot mechanism. That's why it's called an API rather than a hook. React 19 release post
Q3 · What changed

What happened to forwardRef in React 19?

ref is just a prop now. Function components receive ref in props directly, and forwardRef is on a deprecation path with a codemod provided. Small change, but a reliable tell in interviews — writing forwardRef unprompted dates you precisely. React 19 release post
Q4 · What changed

A React Server Component (not SSR — an actual RSC):

No hydration, no client bundle. This is the distinction most people returning to React get wrong, and interviewers probe it precisely because it separates people who read the headline from people who understand the model. Classic SSR renders on the server and ships the component's JS to hydrate it. An RSC never hydrates — it produces a serialised payload the client renders. Option 2 describes SSR; option 4 describes SSG. react.dev — Server Components

Track 2 · Hooks & effects

Q5 · Hooks

Which of these is a legitimate use of useEffect in 2026?

Effects are for synchronising with the outside world. Subscriptions, browser APIs, non-React widgets. The other three are the canonical mistakes: derived values should be computed during render, and resetting state on prop change is done with a key, not an effect. This single page is the highest-value read for someone returning from 2024 — most of what "everyone did" then is now explicitly discouraged. You Might Not Need an Effect
Q6 · Hooks

In development, StrictMode mounts a component, unmounts it, then mounts it again. Why does React do this?

It's a cleanup audit. If your effect is correctly symmetrical, a double mount is invisible. If it isn't, you get a duplicated subscription or a double fetch — which is the bug it's designed to expose. Candidates who describe this as "React being annoying in dev" signal they've never reasoned about effect symmetry. react.dev — StrictMode
Q7 · Hooks

When do you genuinely need useLayoutEffect over useEffect?

Before paint, to avoid a visible flicker. Measuring a tooltip's height to position it is the standard example. It blocks paint, so it's a performance cost you take only to prevent a flash of wrong layout — and it doesn't run during SSR, which is its own trap.
Q8 · Hooks

What is the value of count after one click?

const [count, setCount] = useState(0);

function handleClick() {
  setCount(count + 1);
  setCount(count + 1);
  setCount(count + 1);
}
1, because of the closure — not because of deduplication. All three calls read count as 0 from the render they were created in, so all three say "set it to 1". The fix is the updater form: setCount(c => c + 1), which reads the pending value instead. Option 4 gets the right number for the wrong reason, which in an interview is worse than being wrong — it reveals the mental model.

Track 3 · Rendering & performance

Q9 · Rendering

A parent re-renders. <Child /> is written directly in the parent's JSX, is not memoised, and takes no props. Does Child re-render?

Yes. Re-rendering is the default, top to bottom. Props have nothing to do with it — "my component has no props so it won't re-render" is one of the most common senior-level misconceptions. Option 3 is a real mechanism, but it only applies when the element is passed in as children from a higher component, so its identity is stable across the parent's render. That distinction is worth knowing cold. Developer Way — re-renders guide
Q10 · Rendering

Using the array index as a key breaks what, specifically?

Identity. Keys tell the reconciler which element is "the same" across renders. With index keys, inserting at the front means every element's key shifts, so React matches the wrong DOM nodes and the wrong state — the classic symptom is a typed-in input value or a checkbox jumping to the wrong row. Say that in an interview, not "it's bad practice."
Q11 · Rendering

Which metric replaced First Input Delay as a Core Web Vital?

INP, since March 2024. A pure "were you away?" question, and an easy one to fail. FID only measured the delay before the first interaction's handler started. INP measures the full latency to the next paint, across all interactions — much harder to game, and much more likely to expose a React app that re-renders too much. web.dev — INP
Q12 · Rendering

A 10,000-row table janks badly on scroll. What is the first move?

Virtualisation — the problem is 10,000 DOM nodes, not React. Memoising rows optimises the wrong layer: you'd be making re-renders of an already-fatal DOM cheaper. This question separates people who reach for React knobs from people who diagnose the actual bottleneck first, which is exactly the senior/staff line.

Track 4 · TypeScript

Q13 · TypeScript

What does satisfies give you that a plain annotation does not?

Validation without widening. Annotating const routes: Record<string, string> loses the literal keys. satisfies Record<string, string> checks the same constraint but keeps routes knowing its exact keys, so routes.home still type-checks. Total TypeScript — satisfies
Q14 · TypeScript

Why write this generically rather than typing items as unknown[]?

function List<T>(props: {
  items: T[];
  render: (item: T) => ReactNode;
}) { /* … */ }
The generic carries the relationship. With unknown[] the callback receives unknown and every call site has to narrow or cast. The point of a type parameter is to express "these two things are the same type" — that's the whole idea, and it's the foundation of every harder generics question you'll get at staff level.
Q15 · TypeScript

You model request state as a discriminated union rather than { status; data?; error? }. The main win is:

You delete a class of bug at the type level. The optional-fields version lets you write status: 'loading' alongside a populated error, and forces data! assertions at every use. The union makes the compiler prove data exists in the success branch. This is a genuinely staff-flavoured answer — it's about designing away failure modes, not about syntax.
Q16 · TypeScript

The difference between unknown and any:

unknown is the safe top type. Anything is assignable to it, but you can do nothing with it until you narrow. any switches the checker off and the unsoundness spreads through everything it touches. "Use unknown at the boundary, narrow inward" is the answer that reads as senior.

Track 5 · Platform & architecture

Q17 · Platform

What is logged, and in what order?

console.log('a');
setTimeout(() => console.log('b'), 0);
Promise.resolve().then(() => console.log('c'));
console.log('d');
Synchronous, then microtasks, then macrotasks. a and d run inline. The promise callback is a microtask and drains as soon as the call stack empties. The setTimeout is a macrotask and waits for the next tick, however small the delay. Being able to say "microtask queue drains before the next macrotask" out loud is a standard senior checkpoint.
Q18 · Platform

You build a custom dropdown out of divs. What is the minimum for it to be genuinely accessible?

Roles alone are not enough — behaviour is the hard half. Arrow-key navigation, Escape to close, focus returning to the trigger, aria-expanded and aria-activedescendant kept in sync. ARIA describes what a widget is; it does not make it behave. Accessibility questions are an increasingly common senior filter and a cheap place to stand out, because most candidates answer at the aria-label level. ARIA Authoring Practices — Combobox
Q19 · Platform

In a feed, "optimistic update" on posting a comment means:

Assume success, then roll back on failure. The interesting half is what you say next, unprompted: how you key the temporary item, what happens on failure, and how you avoid the flash when the real item replaces the fake one. React 19 ships useOptimistic for exactly this. TkDodo — optimistic updates
Q20 · Platform

The main cost of a micro-frontend architecture is:

Payload and coherence. Independent deploys are the benefit you're buying; the price is shipping React three times, drifting design systems, and a UX that feels stitched together. Options 3 and 4 invert the trade-off entirely. Staff-level answers name the cost and the org condition that justifies paying it — usually "multiple teams whose release cadences genuinely conflict."

Two things a quiz cannot measure

Multiple choice tests recognition. Interviews test production under pressure. These two tasks close that gap, and they matter more than the twenty questions above — do them before our next session.

Task A — 45 minutes, timed, no AI

Build a typeahead search input in React + TypeScript from a blank Vite app. Requirements: debounced input, a fetch against any public API, a loading state, an error state, keyboard navigation through results with arrow keys and Enter, and cancellation of stale requests.

Set a real timer. Talk out loud the whole time, as you would in the interview. Do not look at reference implementations. If you don't finish, stop at 45 minutes anyway — where you stopped is the measurement.

Report back: how far you got, what you had to look up, and where you stalled. "I couldn't remember the AbortController API" and "I couldn't decide how to structure the state" are completely different diagnoses and lead to different lessons.

Task B — 20 minutes, out loud

Record yourself answering: "Design the frontend for a Twitter-style news feed." Twenty minutes, speaking, no notes. Then listen back — that part is unpleasant and it is the entire point.

Tell me: did you have a structure, or did you wander? Most people who have never done a frontend system design round wander, and the fix is a framework (RADIO), not more knowledge. Knowing which of those two problems you have determines the entire system design track.
