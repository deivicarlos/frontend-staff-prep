The idea, once

A render is a snapshot. Each render gets its own props, its own state values, its own event handlers, and its own effects — and none of them ever change. A re-render doesn't update the old snapshot. It makes a new one.

React's own docs put it this way:

"A state variable's value never changes within a render, even if its event handler's code is asynchronous… Every render (and functions inside it) will always 'see' the snapshot of the state that React gave to that render."
— react.dev, State as a Snapshot

Hold that sentence. We're going to derive all four of your misses from it, and you should try to see each one coming before I explain it.

Derivation 1 — why three increments make one (Q8)

const [count, setCount] = useState(0);

function handleClick() {
  setCount(count + 1);
  setCount(count + 1);
  setCount(count + 1);
}
Predict, then reveal

In the render where count is 0, rewrite those three lines substituting the actual value React gave that render. Then say what the fix is.

Substituting the snapshot value makes it obvious:

setCount(0 + 1);
setCount(0 + 1);
setCount(0 + 1);

count is a const in that render. It is not a live reference to "the current count" — it is the number 0, baked in. So you queued "set it to 1" three times.

The fix is the updater form, which asks React for the pending value instead of reading the snapshot:

setCount(c => c + 1);
setCount(c => c + 1);
setCount(c => c + 1);   // → 3

Note which wrong answer you'd have given. In the calibration, option 4 said "React deduplicates the identical calls." It arrives at the right number, 1, through a completely fictional mechanism. In an interview that's worse than answering 3, because the follow-up question — "so what happens with the updater form?" — has nowhere to go. Queueing a series of state updates

The same snapshot rule explains async. If handleClick does setTimeout(() => alert(count), 3000) and you click, then click four more times, the alert still shows the count from the render that created that timeout. Interviewers love this one because it looks like a bug and isn't.

Derivation 2 — why the child re-renders anyway (Q9)

If a render is "call the component function to produce a snapshot," then a re-render is literally calling that function again. And calling a function runs its whole body — including the lines that create the child elements.

Predict, then reveal

Parent re-renders. Which of these Childs re-render, and why does the answer differ between them?

function A() {                      function B({ children }) {
  return <div><Child /></div>;        return <div>{children}</div>;
}                                   }
                                    // used as: <B><Child /></B>

A re-renders its Child. B does not.

In A, re-running the function body evaluates <Child /> again, producing a new element object. React sees a new element and re-renders it. Props never entered into it — "my component takes no props so it won't re-render" is the misconception, and it's a very common one at senior level.

In B, children was created by B's parent, in a render that didn't happen. So the element object is referentially identical to last time, React bails out, and Child is skipped.

This is why "lift the expensive subtree into children" is a real optimisation, and one worth naming out loud in a system design round — it costs no memo, no dependency array, and no compiler. Developer Way — re-renders guide

Say this precisely in interviews: re-rendering is the default and it is cheap. React re-renders the subtree, diffs the result, and touches the DOM only where the output actually changed. Candidates who say "re-renders are bad" get pushed on it; the correct framing is that re-renders are normal and only expensive renders are worth preventing.

Derivation 3 — what effects are actually for (Q5)

If a render is a snapshot of your UI, then an effect is the step that runs after that snapshot reaches the screen, to make the outside world agree with it. React's words:

"Effects let you specify side effects that are caused by rendering itself, rather than by a particular event… This is a good time to synchronize the React components with some external system (like network or a third-party library)."
— react.dev, Synchronizing with Effects

The word doing the work is external. If the thing you're syncing lives inside React, you don't need an effect — you need to compute it while rendering.

Predict, then reveal

Both of these are common 2022-era code. Neither should use an effect. Rewrite them.

// 1
const [fullName, setFullName] = useState('');
useEffect(() => {
  setFullName(first + ' ' + last);
}, [first, last]);

// 2 — reset the form when a different user is selected
useEffect(() => {
  setDraft('');
}, [userId]);

1 — just calculate it. No state, no effect:

const fullName = first + ' ' + last;

The effect version renders twice for every change (once with stale data, once corrected) and adds a state variable that can drift out of sync. If it's derivable from props or state, derive it during render.

2 — use a key. Resetting state on a prop change isn't an effect, it's an identity change:

<UserForm key={userId} user={user} />

A different key tells React this is a different component instance, so all its state is thrown away and rebuilt. One line, no effect, no flash of the previous user's draft.

Both patterns are on You Might Not Need an Effect, which is the page I flagged in lesson 1 and which you should now actually read — you'll recognise your own old code in it. That recognition is the point.

The rule that fits in one breath: events for things caused by an interaction; render for anything you can calculate; effects only for synchronising with something outside React.

Derivation 4 — why StrictMode mounts twice (Q6)

If an effect's job is "sync the outside world to this snapshot," then when the snapshot goes away the effect must un-sync. Setup and cleanup have to be symmetrical — connect/disconnect, subscribe/unsubscribe, fetch/cancel.

Predict, then reveal

In dev, this logs "Connecting…" twice and you get two live connections. What is the bug, and what would a correct version look like?

useEffect(() => {
  const connection = createConnection(roomId);
  connection.connect();
}, [roomId]);

There is no cleanup. The effect opens a connection and never closes it, so every remount — and every roomId change — leaks one.

useEffect(() => {
  const connection = createConnection(roomId);
  connection.connect();
  return () => connection.disconnect();
}, [roomId]);

React's framing:

"By remounting your component, React verifies that navigating away and back would not break your code… When you implement the cleanup well, there should be no user-visible difference between running the Effect once vs running it, cleaning it up, and running it again."

So the double-mount is not React being awkward in development. It is a free automated test for the most common effect bug there is, and it only happens in development — production mounts once.

Why this matters in an interview: "StrictMode double-invokes, it's annoying, I disable it" is a genuinely bad answer that some candidates give unprompted. The good answer is one sentence: it's probing whether my effects are symmetrical, and if it breaks something, my cleanup is wrong.

Retrieval check

Same four ideas, different clothes. Answer from the model, not from memory of what you just read — that's the difference between fluency and storage.

Q1 · Snapshot

You click the button once, then immediately click it four more times. Three seconds later, what does the alert show?

const [count, setCount] = useState(0);

<button onClick={() => {
  setCount(c => c + 1);
  setTimeout(() => alert(count), 3000);
}}>
0. The first click's handler belongs to the render where count was 0, and the closure captured that number. Later renders make new handlers; they don't reach back and update this one. Note the updater form in the same handler works fine — c => c + 1 doesn't read the snapshot at all.
Q2 · Re-render

React Compiler is enabled, so memoisation is automatic. Which of these still needs you to think about it?

The list. The compiler handles referential identity — that's exactly what automatic memoisation is. It cannot tell you that mounting 10,000 DOM nodes is the wrong architecture. This is the durable distinction: tooling has absorbed the mechanical optimisations, so what interviews now test is whether you can identify the structural ones. Same lesson as Q12 in your calibration, which you got right.
Q3 · Effects

A search page holds query in state and shows filtered results. Where does the filtering belong?

During render. It's derivable from state you already have, so it isn't external, so it isn't an effect. Option 2 is the 2022 habit: it double-renders and can show stale results for one frame. Option 3 splits one source of truth into two places that can disagree. If the filtering is genuinely expensive, the answer is memoisation (or the compiler), not relocation.
Q4 · Effects

Which of these is not symmetrical, and would therefore be caught by StrictMode's remount?

The analytics event. There's no "un-send" for it, so the double-mount sends two purchases. That's the real tell: it isn't just missing a cleanup, it is uncleanable — which means it was never an effect. Sending a purchase event is caused by a user action, so it belongs in the event handler. StrictMode surfaces the design error, not just the code error, and saying that out loud is a strong answer.
Q5 · Snapshot

Why does React give each render its own event handlers instead of reusing one?

Consistency. A handler that fired during a given render should behave according to what was on screen when the user clicked — not according to whatever state has arrived since. The "stale closure" you keep hearing described as a footgun is that guarantee, viewed from the wrong angle. Framing it as a deliberate consistency guarantee rather than a gotcha is a noticeably senior answer.
Q6 · Re-render

A context provider holds { user, theme } in one value. Theme changes. What happens to a component that only reads user?

It re-renders, and memo will not save it. Context is all-or-nothing: any consumer re-renders when the provider's value changes identity, regardless of which part it reads. This is the standard follow-up to "how would you scale this context," and the answers are: split into multiple contexts by update frequency, or move to an external store with selectors (Zustand, Redux, useSyncExternalStore). Worth having ready — it comes up constantly in frontend system design.

Saying it out loud

Knowing this and performing it are different skills, and interviews only test the second. Rehearse these until they're one breath each:

  • "Each render is a snapshot — props, state and handlers are frozen for that render." This one sentence answers every stale-closure question you'll ever get.
  • "Re-rendering is the default and it's cheap; React only touches the DOM where output changed." Prevents the trap of sounding like you think re-renders are inherently bad.
  • "Events for interactions, render for anything derivable, effects only for external systems."
  • "StrictMode's double-mount checks my effects are symmetrical."
