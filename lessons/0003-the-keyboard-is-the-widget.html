Why this is worth thirty minutes and not a footnote. In a typeahead brief, keyboard navigation is the requirement that most separates senior from mid. Debounce, loading and error are things every candidate writes. The keyboard is where people either produce a coherent interaction model or produce onKeyDown with two if statements and no idea what happens at the end of the list.

It is also the one place where the accessibility answer and the correct answer are the same answer. You don't bolt ARIA on afterwards — the ARIA attributes are the state you had to track anyway.

The idea, once

A composite widget has two focuses. There is DOM focus — where keystrokes actually go — and there is the widget's own idea of which item is active. In a typeahead these must be in different places at the same time, and every technique below exists to reconcile that.

That sentence is the whole lesson. Hold it, and the rest derives.

Derivation 1 — why you can't just call .focus()

The obvious implementation of ArrowDown is "move focus to the next result." Try to see why that cannot work before reading on.

Predict, then reveal

The user has typed tolk and eight results are showing. They press ArrowDown, and you call liRef.current.focus() on the first result. They now press i, meaning to continue typing tolkien. What happens, and what does that tell you about where DOM focus has to live?

The i goes nowhere. DOM focus is on an <li>, not the input, so the character is dropped — or worse, it triggers the browser's type-ahead-to-select behaviour on the list. The user has to click back into the field. You have broken typing in order to implement typing.

So the constraint is absolute: in a combobox, DOM focus never leaves the input. Which leaves you needing to tell a screen reader that a different element is the active one, without moving the browser's focus there. That is exactly the problem aria-activedescendant exists to solve.

The APG is unambiguous about it:

"DOM focus is maintained on the combobox and the assistive technology focus is moved within the listbox using aria-activedescendant."
— W3C ARIA Authoring Practices Guide, Combobox Pattern

Derivation 2 — the two techniques, and how to choose

There are exactly two sanctioned ways to manage focus inside a composite widget. Knowing both and knowing why you picked one is a strong interview answer; knowing one is a mid answer.

A · aria-activedescendant — focus stays put, a pointer moves

The container is in the tab sequence and carries an attribute naming the active child by id. Nothing is focused but the container.

<input
  role="combobox"
  aria-expanded={open}
  aria-controls="results"
  aria-autocomplete="list"
  aria-activedescendant={active >= 0 ? `opt-${active}` : undefined}
/>
<ul id="results" role="listbox">
  <li id="opt-0" role="option" aria-selected={active === 0}>…</li>
</ul>

The cost is that you own everything the browser would normally have done for you. The APG spells out the obligation:

"When the container element receives DOM focus, draw a visual focus indicator on the active element and ensure the active element is scrolled into view."
— APG, Developing a Keyboard Interface

Nothing is focused, so nothing gets :focus styling and nothing auto-scrolls. Both are on you.

B · Roving tabindex — real focus, one tab stop

Exactly one child has tabindex="0"; every sibling has tabindex="-1". Arrow keys move the 0 and then call .focus(). The whole group is one tab stop, which is the point — a toolbar of twelve buttons shouldn't cost twelve tabs.

"…set tabindex="0" on the element that will initially be included in the tab sequence and set tabindex="-1" on all other focusable elements it contains."
— APG, Developing a Keyboard Interface

And the reason to prefer it when you can:

"One benefit of using roving tabindex rather than aria-activedescendant to manage focus is that the user agent will scroll the newly focused element into view."

The decision rule, in one line: if the user must keep typing while navigating, DOM focus can't move, so it's aria-activedescendant — combobox, typeahead, autocomplete. If they don't need to type, move real focus with roving tabindex and get focus styling and scrolling for free — toolbar, tabs, menu, radio group, tree, grid.

So your typeahead is technique A. Say the trade-off out loud when you build it: "I'm using aria-activedescendant because focus has to stay in the input for typing — which means I owe the highlight styling and the scroll-into-view myself." That single sentence demonstrates you know both techniques and chose.

Derivation 3 — the state is one number, and it has an identity problem

The entire keyboard layer is one piece of state:

const [active, setActive] = useState(-1);   // -1 = nothing highlighted

-1 rather than 0 is deliberate: on a fresh set of results nothing is highlighted, so Enter does nothing rather than selecting a row the user never looked at.

Predict, then reveal

The user has arrowed down to active === 5. They then type one more character; the debounce fires and a new search returns two results. What is on screen, and what is the bug class?

active is still 5, the list has indices 0 and 1, so nothing is highlighted and aria-activedescendant points at an id that no longer exists. Press Enter and you read results[5] — undefined — and crash, or silently select nothing.

This is an identity bug, and you should recognise the shape by now. An index is a position, not a thing. When the list it indexes into is replaced, the number is still valid and its meaning is gone — the same reason key={`${index}-${title}`} in your rebuild wasn't a stable key, and the same reason a constant queryKey broke attempt one.

The fix is to reset the highlight whenever the thing it points into changes:

useEffect(() => { setActive(-1); }, [results]);

Interview-grade follow-up, worth volunteering: "if I wanted the highlight to survive a refresh of the same search, I'd track the selected item's id instead of its index and re-derive the position — an id keeps its meaning across a new array, an index doesn't."

Derivation 4 — the interaction contract

This is the part that is pure knowledge, so here it is as a table. The APG marks some of these optional; the ones you must have for a credible answer are marked required.

KeyBehaviour
ArrowDownOpen the popup if closed; otherwise move to the next optionrequired
ArrowUpMove to the previous option; from nothing, opens at the last optionrequired
EnterAccept the active option, close the popuprequired
EscapeDismiss the popup. Optionally also clear the inputrequired
Home / EndJump to first / last optionoptional
Alt+ArrowDownOpen the popup without moving the active optionoptional

Three details that separate a considered implementation from a guessed one:

  • Wrap or clamp — pick one on purpose. Wrapping (last → first) suits a short result list; clamping suits a long one, where wrapping feels like the list broke. Either is correct. Having no opinion is the wrong answer, and so is being surprised by the question.
  • preventDefault() on the arrows. Otherwise ArrowUp jumps the text cursor to the start of the input while your highlight moves — two things happening per keypress. This is the single most common bug in hand-rolled typeaheads.
  • Escape's focus behaviour depends on the technique. The APG says Escape "closes the popup and returns focus to the combobox" — but with aria-activedescendant, focus never left, so there is nothing to return. That is only a real step under roving tabindex. Noticing that the spec sentence doesn't apply to your architecture is exactly the kind of remark that reads as senior.

Derivation 5 — cleanup, away from timers

In your rebuild you wrote this, and it is flawless:

const timerId = setTimeout(() => setDebounced(txt), msDelay);
return () => { clearTimeout(timerId); };

And in the same forty-five minutes, in the same codebase, you built an AbortController, destructured its signal, threaded it through your API module into fetch — and returned nothing from the effect. So nothing ever aborted. Ninety percent of the machinery, no trigger.

Two data points make a pattern: you have stored cleanup as a thing you do after setTimeout, rather than as a property of effects. That's my fault as much as yours — lesson 2 taught the principle and every example I used was a timer. So here it is on three surfaces that aren't.

// 1 · A listener. Close the popup on an outside click.
useEffect(() => {
  const onDown = (e) => { if (!rootRef.current?.contains(e.target)) setOpen(false); };
  document.addEventListener("pointerdown", onDown);
  return () => document.removeEventListener("pointerdown", onDown);
}, []);

// 2 · An in-flight request. The one you missed.
useEffect(() => {
  const controller = new AbortController();
  load(controller.signal);
  return () => controller.abort();
}, [debounced]);

// 3 · An observer.
useEffect(() => {
  const ro = new ResizeObserver(measure);
  ro.observe(listRef.current);
  return () => ro.disconnect();
}, []);

Same shape every time. Say it as one rule and it stops being three facts:

If the effect body started anything — a timer, a listener, a request, an observer, a subscription — the cleanup stops that same thing. React will re-run the effect, and the cleanup is what makes the previous run stop mattering.

One trap specific to the request case, which is why cancellation looked optional in your code. Aborting makes fetch reject, so it lands in your catch. If you treat that as a failure you will flash an error banner every time the user types a character:

catch (err) {
  if (err instanceof DOMException && err.name === "AbortError") return;  // expected, not a failure
  setState({ status: "error", message: "Could not load results" });
}

The whole keyboard layer

Everything above, assembled. This is roughly twelve minutes of typing once you know it, which is the point of learning it now rather than discovering it on a clock.

function onKeyDown(e) {
  if (!open || results.length === 0) return;

  switch (e.key) {
    case "ArrowDown":
      e.preventDefault();
      setActive(i => (i + 1) % results.length);          // wrap
      break;
    case "ArrowUp":
      e.preventDefault();
      setActive(i => (i <= 0 ? results.length : i) - 1); // wrap, and -1 → last
      break;
    case "Home":
      e.preventDefault();
      setActive(0);
      break;
    case "End":
      e.preventDefault();
      setActive(results.length - 1);
      break;
    case "Enter":
      if (active >= 0) { e.preventDefault(); select(results[active]); }
      break;
    case "Escape":
      setOpen(false);
      setActive(-1);
      break;
  }
}

Note setActive(i => …) rather than setActive(active + 1). Holding ArrowDown fires repeat events faster than React re-renders, and the updater form is what stops them all reading the same snapshot — lesson 2's derivation 1, showing up somewhere it actually bites.

Then the scroll obligation you took on by choosing aria-activedescendant:

useEffect(() => {
  if (active < 0) return;
  document.getElementById(`opt-${active}`)
    ?.scrollIntoView({ block: "nearest" });
}, [active]);

block: "nearest" matters — the default yanks the list even when the row is already visible.

Retrieval check

Six questions. Two on the focus model, two on the interaction contract, two on cleanup — the last pair deliberately on surfaces this lesson did not use as its examples, because that is the difference between holding a principle and having memorised a snippet.

Q1 · Focus model

In a typeahead, why is calling .focus() on the highlighted <li> wrong?

Typing breaks. The first option is true in isolation — you would need tabindex="-1" — but it's a mechanical detail, not the reason. The reason is behavioural: a combobox is a text field the user is still typing into, so DOM focus cannot leave it, which is precisely why aria-activedescendant exists.
Q2 · Focus model

You're building a toolbar of twelve icon buttons with arrow-key navigation. Which technique, and what do you get for free?

Roving tabindex, and you get real focus. Nobody is typing into a toolbar, so DOM focus is free to move — and once it does, the user agent scrolls the focused element into view and :focus-visible works, both of which you would otherwise owe by hand. Both techniques give you one tab stop, so that isn't the discriminator. Option 4 has it backwards: under aria-activedescendant nothing is focused, so there is nothing to style.
Q3 · Contract

active is 5. A new search returns two results. What must happen, and why is it the same bug you've hit before?

Reset on change. Clamping keeps a highlight the user never asked for on a row they never looked at, and Enter then selects it. Nothing is discarded automatically — active is state and state persists across renders; that persistence is the bug. This is the identity family again: an index stays numerically valid while its meaning evaporates, exactly like an index-based key or a frozen queryKey. Track the item's id if you want the highlight to survive.
Q4 · Contract

Your arrow handling works, but ArrowUp also jumps the text cursor to the start of the input. What's missing, and what does that tell you about the class of bug?

preventDefault(). The caret move is the input's default action, not another listener, so stopping propagation does nothing — that distinction is the point of the question. Moving the handler to the <ul> is worse: it never receives the key, because focus is in the input. onKeyUp fires after the browser has already acted. Whenever you implement a key that the platform already means something by, you are overriding rather than adding.
Q5 · Cleanup

An effect creates an IntersectionObserver, calls .observe() on a row, and returns nothing. The list re-renders on every keystroke. What is the failure?

They pile up. Each run constructs another observer and none of the previous ones stop, so callbacks multiply with keystrokes. Nothing rebinds and nothing throws — that's what makes it nasty: no error, just growing work. Cleanup is ro.disconnect(). Same shape as clearTimeout, same shape as controller.abort(), same shape as removeEventListener. If the body started it, the cleanup stops it.
Q6 · Cleanup

You add return () => controller.abort() to your fetch effect. Now an error banner flashes on almost every keystroke. What did you get wrong?

The catch can't tell cancellation from failure. A successful abort is a rejection — it arrives as a DOMException named AbortError — so it must be filtered out before you set an error state. This is the half of requirement 6 that isn't the cleanup line, and it's why your rebuild's catch couldn't have been extended into requirement 4 as written. React 18+ no longer warns about setting state after unmount, so option 4 is out of date.

Saying it out loud
