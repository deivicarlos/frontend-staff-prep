The constraint ledger

You already know most of how a feed works. You lost the design probe because a constraint you had just described was gone one question later. This lesson is RADIO used as a way to stop that from happening, not a list of steps to recite.

Lesson 05 · Frontend system design · ~30 minutes · have a timer ready

Why this lesson

Probe"Design a news feed": you opened with Tailwind, react-query and virtualization. You asked no questions, so you gathered no requirements.
Q2→Q3You described new posts being prepended and the scroll offset being compensated. One question later you chose ?offset= pagination, which prepending breaks. You said: "not sure why".

0005"The operator needs to know" did not turn into "render an error state". That is the same skill: turning prose into a constraint you can act on.

None of these are gaps in what you know. Each decision was made on its own, and nothing checked it against what you had already said. The fix is structural: write the constraints down, number them, and have every later decision cite one.

The percentages come from GreatFrontEnd's playbook, and the minutes are those percentages applied to a 45-minute round. The guide frames the first step as "Understand the problem thoroughly and determine the scope by asking a number of clarifying questions." The step you skipped is only 10% of the clock, and it is where everything in the other 90% gets decided.

The idea, once. Requirements aren't a phase you finish and move on from. They are a ledger. Every later decision is an entry that has to cite the constraint that forced it. A decision that cites nothing is a preference. A decision that contradicts an earlier line is the bug interviewers are listening for.

Application 2: replay your own Q2 → Q3

Predict, then reveal

Ledger line C1: the feed's head moves. The API offers both ?offset=&limit=20 and ?cursor=&limit=20. The user has loaded two pages (posts 1–40). While they read, 30 new posts arrive at the top. They scroll and you request page 3. With offset, what exactly comes back? And what happens with offset if 3 posts are deleted from the top instead?

30 prepended: ?offset=40 now points at what used to be post 11. You get old posts 11–30 again, all of them duplicates of rows already on screen.

3 deleted: ?offset=40 now points at what used to be post 44. Old posts 41–43 are never shown. Duplicates at least look like a bug. Silent gaps don't look like anything.

A cursor names the last item you saw (for example "posts older than id p_9f2"). Inserts and deletes elsewhere can't move it. GreatFrontEnd's feed write-up: "When new posts are inserted into the feed, offsets can shift, leading to duplicate or missing items", and "For a news feed, cursor-based pagination is the clear choice."

Cursor vs offset, the full comparison

Offset / page numberCursor
Data changes while pagingDuplicates or skipped itemsStable
Deep pagesThe database skips N rows, so it gets slower as N growsSeeks from an index, so the cost stays flat
Jump to page 37, show "page 3 of 50"YesNo, it only goes to the next page (or the previous one)
Right forAdmin tables, search results with page numbers, mostly static dataFeeds, chat, logs, anything with a moving head

Offset isn't wrong. It's wrong under C1. That is the whole point of the ledger: the same choice is right or wrong depending on a line written ten minutes earlier.

useInfiniteQuery: one entry, many pages

Your ['posts', 'page3'] gives every page its own cache entry. With TanStack, an infinite feed is one query whose data is { pages, pageParams }. These are the v5 facts, checked against the docs and the installed type definitions:

initialPageParamRequired in v5. This is the cursor for the first page, e.g. null.
getNextPageParamRequired. (lastPage, allPages, lastPageParam, allPageParams) => TPageParam | undefined | null
hasNextPagetrue when getNextPageParam returns anything other than null or undefined.
Refetch"each group is fetched sequentially, starting from the first one", so with 15 pages loaded, a refetch is 15 requests one after another.
fetchNextPage during a fetchThe docs warn this "runs the risk of overwriting data refreshes happening in the background". Guard it with !isFetching.
maxPagesCaps how many pages are kept. It requires getPreviousPageParam as well, so trimmed pages can be fetched again when the user scrolls back up.
Write it, 4 minutes

GET /api/feed?cursor=<id>&limit=20 returns { items: Post[], nextCursor: string | null }. The first page is requested with no cursor. Write the useInfiniteQuery call, the flattened list, and the handler your scroll sentinel calls. Check where the cursor comes from: it has to come from the server's answer, not from a counter.

const { data, fetchNextPage, hasNextPage, isFetching } = useInfiniteQuery({
  queryKey: ["feed"],
  queryFn: ({ pageParam, signal }) => fetchFeed(pageParam, signal),
  initialPageParam: null as string | null,
  getNextPageParam: (lastPage) => lastPage.nextCursor, // null ends the feed
});

const posts = data?.pages.flatMap((p) => p.items) ?? [];

function onSentinelVisible() {
  if (hasNextPage && !isFetching) fetchNextPage();
}

Check where each part sits:

  • The key has no page in it. The page lives in pageParam, which TanStack stores in data.pageParams.
  • The cursor comes from lastPage.nextCursor. Writing allPages.length * 20 would be offset pagination with a different name.
  • The guard is !isFetching, not only !isFetchingNextPage. A background refetch counts too.
Carry a constraint

The user has scrolled 15 pages deep and likes a post. A teammate writes onSuccess: () => queryClient.invalidateQueries({ queryKey: ["feed"] }), the fix you shipped in 0005. Using ledger lines C1, C4 and C5, what does it cost here, and what do you write instead?

Cost: the refetch is sequential from page 1, so that's 15 requests one after another on a mobile connection (C4). Because the head moved (C1), the refetched pages can also differ from the ones on screen, and rows shift under the reader.

Instead: queryClient.setQueryData(["feed"], old => …), mapping over old.pages and changing only that one post. Do it optimistically in onMutate and roll back on error (C5). In 0005, invalidating was right: 12 rows, one page, and filters that all needed the change. The same technique is right or wrong depending on the ledger.

The sentence to have ready

"Before I draw anything, I'll pin down the constraints and number them, so every decision I make after this points back to one. If a later choice contradicts a line, that's the bug."

Say it and then do it. Keep the ledger visible on the board and point at it when you choose something ("cursor, because of C1"). Interviewers score whether your decisions are justified. Pointing at a numbered line makes the justification visible.

Retrieval check: a new prompt, the same claim

This one tests the lesson's claim directly: a constraint given early has to be what decides a later answer. Set a 10-minute timer. Write each answer and cite the ledger line it depends on. An answer that cites nothing doesn't count, even if it's right.

The brief: a chat channel (like Slack)

You clarified the requirements and got these answers. Write them into a ledger first:

  • Channels have years of history. Users open a channel at the newest message and scroll up for older ones.
  • New messages arrive in real time at the bottom.
  • Messages can be edited and deleted by anyone with rights, at any time.
  • Links to a specific message exist (from search and notifications), and following one opens the channel at that message, possibly years back.
  • Mobile web is supported.
0 · The ledger

Write C1…Cn, one line each.

C1 history is loaded upward from the newest · C2 the head moves (real time) · C3 items change and disappear anywhere (edit/delete) · C4 you can enter anywhere (deep link) · C5 mobile limits. Your wording will differ. What matters is that C3 and C4 are separate lines.

1 · Pagination scheme

Deep links (the fourth bullet) make "page 37" look tempting. Which scheme do you choose, and which line rules the other one out?

Cursor, anchored on a message id. C3 rules out offset: deletes anywhere shift every offset after them, so "page 37" means something different each time you ask. C4 doesn't need page numbers. It needs "the messages around id X", which is a cursor request (?around=msg_123, then ?before= and ?after=). If you chose page numbers because of C4, that's the Q2→Q3 pattern again: the line that looked like it helped overrode the line that forbids it.

2 · TanStack model

What is the query key, and which of getNextPageParam / getPreviousPageParam do you need? Cite the lines.

One infinite query per channel, ["messages", channelId], with no page number in the key. You need both directions. Older messages load upward (C1) and, after a deep link, newer ones load downward toward the present (C4). C5 adds maxPages, which also requires getPreviousPageParam. The initialPageParam is the anchor: "latest", or the linked message's id. If the anchor goes in the key (["messages", channelId, anchorId]), a deep link and a normal open become separate cache entries. That's acceptable, but say it out loud.

3 · A message arrives while they read history

The user is 200 messages up, reading. A new message arrives (the real-time bullet). What happens on screen, and how does it get into the cache? Cite the lines.

Don't scroll the user, and don't refetch. Write the message into the newest page with setQueryData and show a "new messages ↓" pill (C2). Only auto-scroll when they were already at the bottom. If they arrived by deep link, the newest page may not be loaded at all (C4). Then the message goes nowhere in the cache, and the pill takes them to the present with a fresh load. Invalidating would refetch every loaded page in sequence (C5).

4 · Someone deletes a message you've loaded

It arrives as a real-time event. What do you do, and what do you not have to do because of decision 1?

Remove it (or mark it deleted) in whichever page holds it, using setQueryData. You don't have to repair pagination. The cursors are message ids, so a hole in the list doesn't move the next request (C3 → decision 1). That is what paying off a constraint looks like: an earlier decision makes a later problem disappear.

Q1 · useInfiniteQuery

A feed has 6 pages loaded and its query goes stale and refetches. What goes over the network?

Sequentially from the first. Each page's param comes from the page before it, so the refetch can't run in parallel. This is why a broad invalidateQueries on a deep feed is expensive, and why maxPages exists.
Q2 · useInfiniteQuery

What does hasNextPage come from?

getNextPageParam. Return null or undefined and the feed ends. The logic that decides this is yours. TanStack never looks at item counts or headers.
Q3 · Pagination

Which product is offset pagination the right choice for?

The invoice table. The data mostly sits still, and the product needs things only offset gives you: a total page count and random access. Every other option has a moving head or holes, which is C1 or C3 from this lesson.
