The browser attaches the cookie

There are two attacks to keep apart. In XSS the attacker's code runs inside your origin. In CSRF the attacker's page makes the victim's browser send a request to you, and the browser attaches your cookie on its own. Token storage, cookie flags and sessions vs JWT all come down to which of the two a choice defends against.

Two attackers

XSS (cross-site scripting)CSRF (cross-site request forgery)
Where the attacker's code runsIn your origin. Same privileges as your own JS.On their own site. It never runs in your origin.
What it relies onYour app rendering attacker-controlled input as codeThe browser attaching your cookies to a request based on its destination, whoever started it
Can it read your responses?YesNo. The same-origin policy blocks the read, but the request has already been sent and acted on
Can it read a cookie?Yes, unless the cookie is HttpOnlyNo, and it doesn't need to
Who is at riskToken in JS storage and cookie sessionsCookie-based auth only. A token your JS puts in an Authorization header isn't attached automatically

OWASP's definition of CSRF: "a malicious web site, email, blog, instant message, or program tricks an authenticated user's web browser into performing an unwanted action on a trusted site." The last row is the trade-off the whole lesson turns on. Moving a token into a cookie removes most of the XSS theft risk and adds CSRF risk.

Why the forged request goes through

CORS only controls whether a page can read a response. A "simple" request (GET, HEAD or POST with a Content-Type of application/x-www-form-urlencoded, multipart/form-data or text/plain, and no custom headers) is sent with no preflight. MDN: the request "IS sent to the server", and the browser only blocks the page from reading the response. A plain HTML <form> always sends a simple request.

Predict, 3 minutes

You're logged in to bank.example, and its session cookie has no SameSite attribute (assume a browser that doesn't default it to Lax). You open evil.example, which contains:

<form method="POST" action="https://bank.example/transfer">
  <input name="to" value="attacker"><input name="amount" value="5000">
</form>
<script>document.forms[0].submit()</script>

(a) Does the transfer happen? (b) The attacker swaps the form for fetch(url, { method: "POST", credentials: "include", headers: { "Content-Type": "application/json" }, body }), and the bank has no CORS configuration. Does that transfer happen?

(a) Yes. It's a simple request, so no preflight runs. The browser attaches bank.example's cookie because the request is going to bank.example. The server sees a valid session and moves the money. The attacker can't read the response, and doesn't need to.

(b) No. application/json isn't a simple content type, so the browser sends an OPTIONS preflight first. The bank doesn't answer with Access-Control-Allow-Origin: https://evil.example and Access-Control-Allow-Credentials: true, so the real POST is never sent.

The trap in (b): if the server also accepts the same JSON when it arrives as text/plain, the attacker sends it that way. It's a simple request again, and the attack works. This is why OWASP's "custom header" defence says to require the header. A header forces a preflight. A content type only forces one if the server refuses every other content type.

Two things to know about the defaults. MDN: "Some browsers use Lax as the default value if SameSite is not specified" (Chromium does). When Lax is only the default, cookies are still sent on cross-site POSTs for two minutes after they were set. So set the attribute explicitly. And OWASP, on using SameSite as your CSRF defence: "useful as a defense-in-depth control but it does not replace a proper CSRF defense."

Two more OWASP points. Login CSRF: the login form needs protection too, because an attacker can log the victim in to the attacker's account. And "XSS can defeat all CSRF mitigation techniques": script running in your origin can read the token and send the header.

Apply, 4 minutes

A BFF session cookie is set as sid=…; HttpOnly; Secure; SameSite=Lax; Path=/ on app.example.com, with no other CSRF defence. That's roughly where your current setup sits. For each attack, write succeeds or blocked, and name the flag or rule that decides it:

  1. evil.com auto-submits a form POST to /api/projects/42/delete.
  2. The API also accepts GET /api/projects/42/delete, and evil.com shows a link to it that the user clicks.
  3. The same GET URL, but in <img src> on evil.com.
  4. A stored XSS on blog.example.com (another team's app) auto-submits the form POST from 1.
  5. A stored XSS inside app.example.com runs fetch("/api/projects/42", { method: "DELETE" }).
  1. Blocked. It's a cross-site POST, and Lax doesn't send the cookie with it.
  2. Succeeds. A link click is a top-level navigation with a safe method, which is exactly Lax's exception. The bug is the state-changing GET. Fix that, not the cookie.
  3. Blocked. An <img> is a subresource request, not a top-level navigation.
  4. Succeeds. blog.example.com and app.example.com are the same site (same registrable domain), so SameSite doesn't apply. Sec-Fetch-Site would say same-site, so a server that accepts only same-origin blocks it. So does a CSRF token.
  5. Succeeds, and no flag can stop it. The request is same-origin and HttpOnly doesn't stop the cookie from being sent. This is the next section.

Score: one point for each correct verdict that names the right rule. A correct verdict with no rule doesn't count, which is how lesson 5 graded decisions too.

XSS: where the token is stored decides what gets stolen

RFC 10017 (OAuth 2.0 for Browser-Based Applications, BCP 212, August 2026) lists what attacker code can do once it runs in your app (§5.1):

PayloadWhat it doesWho it works against
Single-execution token theftReads the current tokens and sends them outTokens that JS can reach
Persistent token theftKeeps stealing each new token (e.g. after every refresh)Tokens that JS can reach
Acquisition of new tokensStarts its own silent authorization flow in a hidden iframe and keeps the resultEvery app that gets its tokens in the browser, wherever it stores them
Proxying requests via the user's browserCalls your API from inside the page while it's openEveryone, cookie sessions included

On the last row, §5.1.4: "It is commonly accepted that this scenario cannot be stopped or prevented by application-level security measures." On storage, §8.5: localStorage "does not protect against unauthorized access from malicious JavaScript", and of localStorage, sessionStorage and IndexedDB, "none of these options can fully mitigate token exfiltration." In-memory storage (§8.4) narrows the exposure, but code running in the same page can still get the token, for example by replacing fetch before your code calls it.

The idea, once. No storage choice defeats XSS. What a storage choice decides is what the attacker leaves with. A token they can reach in JS works from their own machine, after the tab closes, until it expires. An HttpOnly session cookie only lets them act through the open tab, against your backend, where you can see it and end it. Stealing the token outright becomes using the session while the tab is open. The defence against XSS itself is not having XSS: React's escaping, no dangerouslySetInnerHTML on untrusted input, and a strict CSP as a second layer.

That CSP, as OWASP recommends it: script-src 'nonce-{random}' 'strict-dynamic'; object-src 'none'; base-uri 'none'. Use a nonce or a hash, not a list of allowed domains. Allowlist policies have been shown to be routinely bypassable. OWASP is explicit that CSP "should not be relied upon as the only defensive mechanism against XSS."

Defend it, 3 minutes

A teammate's PR: "Security fix: the access token moves from localStorage into a React context, so XSS can't steal it." Write your review comment: what it actually improves, what it doesn't, and what you'd propose instead.

Improves: the token no longer survives a reload or sits on disk, and a generic script that dumps localStorage no longer finds it (§8.4: it "limits the exposure").

Doesn't: an attacker who targets this app can still get it: patch fetch or a prototype and read the header as it goes out (theft), run a silent flow to get a fresh token (acquisition), or simply call the API (proxying). The PR title overclaims.

Instead: if the data is sensitive, take tokens out of the browser entirely. A BFF keeps the tokens on the server and gives the browser an HttpOnly cookie. RFC 10017 §6.1.4.3 "strongly recommended" it for business apps and anything that handles personal data. Add a strict CSP either way. A Staff-level comment approves the small win and names the real fix.

Sessions vs JWT: where the state lives

Server session (opaque ID in a cookie)Self-contained JWT (verified by signature)
StateIn a server store, looked up by the IDIn the token. The server holds nothing
Per-request costA store lookup (e.g. Redis)A signature check. No lookup
Revoke one user nowDelete the session. The next request failsYou can't. It's valid until exp, unless you keep a denylist keyed on jti, which brings back the lookup
LogoutDestroy it on the server (OWASP: invalidate "on both sides, client and server")The client throws the token away, and any copy of it still works
Scales across servicesNeeds a shared storeAny service holding the key can verify it
Session fixationIssue a new ID at login (OWASP: renew "after any privilege level change")Not applicable. A new token is minted at login

The usual answer is "both": short-lived JWT access tokens, so the revocation gap is minutes, and a refresh token or server session that can be revoked. That's lesson 7. For a session ID, OWASP asks for at least 64 bits of entropy, an idle timeout (2–5 min for high-value apps, 15–30 for low-risk ones) and an absolute timeout (typically 4–8 h).

Predict, 2 minutes

Security disables a compromised account at 10:00. The attacker's credential was issued at 09:50. When does the attacker lose access with (a) a server session, (b) a JWT with a 1-hour exp and no denylist, (c) a 5-minute access JWT plus a refresh token that the server revokes at 10:00?

(a) 10:00, on their next request, if disabling the account deletes its sessions. If it doesn't, you have the JWT problem with extra steps. (b) 10:50. (c) No later than 10:05. The access token issued at 09:50 died at 09:55, and the most recent refresh before 10:00 issued one that lasts at most until 10:05. The refresh at that point fails. The trade-off is something you can state as a number: the access token's lifetime is the longest a revoked user keeps access.

The sentence to have ready

"No token storage survives XSS: attacker code in my origin can always call my API. So I pick storage for what an attacker leaves with. With a BFF and an HttpOnly, Secure, SameSite cookie, they leave with nothing usable off the page. The cookie brings CSRF with it, so I add a real CSRF defence on top of SameSite: Fetch Metadata or a required custom header. And I prevent the XSS itself with escaping and a strict CSP."

It covers both attacks, admits what nothing can stop, and says which defence is the primary one and which is the extra layer. Interviewers listen for the last part.

Q1 · SameSite

The cookie is HttpOnly; Secure; SameSite=Lax. Which request started on evil.example arrives with the cookie?

The link click. Lax allows cross-site top-level navigations that use a safe method. That's why a state-changing GET is a CSRF hole even with Lax.
Q2 · XSS vs HttpOnly

Attacker script runs inside your SPA. The session is an HttpOnly cookie. What can the attacker not do?

Read the value. That's the only thing HttpOnly prevents. The cookie is still sent with the script's same-origin requests, which is RFC 10017's "proxying" payload.
Q3 · CORS

evil.example calls fetch on your API with credentials: "include" and Content-Type: application/json. Your API has no CORS configuration. Why doesn't the write happen?

The preflight fails. JSON isn't a simple content type, so the browser asks first, and your API doesn't approve evil.example. If the API also accepts text/plain, there's no preflight and the write happens.
Q4 · Revocation

A user must be cut off immediately. The API uses stateless JWTs with a 1-hour exp and no denylist. When does access actually end?

At exp. The API checks the signature and never asks anyone. Any copy of the token works until then. Revoking it means a denylist (state again), or short lifetimes with a refresh token that can be revoked.
