Why did it render?

Three things make a component render. memo, useMemo and useCallback only touch one of them. useRef and useEffectEvent are how you keep a value without starting one.

Lesson 07 · Hooks, part 1 of 2 · ~30 minutes · Part 2 →

1 · The mechanism: what a render is

A render is React calling your component function to get a new description of the UI. Then React compares it with the previous one and changes the DOM only where they differ. That second step is the commit. A render that produces the same output touches no DOM at all (react.dev, Render and Commit).

A component renders for exactly three reasons:

TriggerDetail
1 · Its own state was setTo a value that isn't Object.is-equal to the current one. Setting the same value skips the render.
2 · Its parent renderedEvery child renders by default, whether or not its props changed.
3 · A context it reads changedEvery consumer of that context renders.

"Its props changed" is not on the list. Props only change because the parent rendered, which is trigger 2, and that already renders the child anyway. This is the part people get wrong (Developer Way, re-renders guide).

The second idea everything here depends on is identity. React compares with Object.is: Object.is(3, 3) is true, but Object.is({}, {}) is false (react.dev, memo). Every {…}, […] and () => … written in a component body is a new object on every render, even when its contents are identical.

Predict, then reveal

You click the button once. Which of Header, List and Footer render? Then: if all three were wrapped in memo, which would render?

function Page() {
  const [count, setCount] = useState(0);
  const [items] = useState(["a", "b"]);
  return (
    <>
      <button onClick={() => setCount(count + 1)}>{count}</button>
      <Header />
      <List items={items} />
      <Footer style={{ color: "gray" }} />
    </>
  );
}

Without memo: all three. Page's state changed (trigger 1), so every child renders (trigger 2). Header has no props and renders anyway.

With memo: only Footer. memo compares each prop with Object.is. Header has no props, so it's skipped. items is the same array from state, so List is skipped. { color: "gray" } is a new object on every render, so Footer renders, and its memo did nothing.

2 · memo, useMemo, useCallback: one job, three parts

All three exist to stop trigger 2. They only work together:

ToolCachesWorth it when
memo(Child)The child's render. It's skipped if every prop is Object.is-equal to last timeThe child is expensive and its parent renders often
useMemo(() => v, deps)The result of a functionAn expensive calculation, or keeping an object prop stable for a memo child
useCallback(fn, deps)The function itself. It's useMemo(() => fn, deps)Passing it to a memo child, or using it as an effect dependency
  • "memo is completely useless if the props passed to your component are always different, such as if you pass an object or a plain function defined during rendering" (memo). That's why useMemo and useCallback exist.
  • The reverse holds too: useCallback has "no benefit" unless a memo child or a hook's dependency array consumes the function (useCallback).
  • memo does not stop triggers 1 and 3: the component's own state changing, or a context it reads changing (memo).
  • Cheaper fixes, with no memo at all: move the state down into the component that uses it, or pass the expensive part as children (lesson 2).
  • React Compiler 1.0 (October 2025) inserts this memoization at build time. With it, "you can safely remove React.memo" (memo). A legacy codebase you're migrating probably isn't on the compiler yet, so you still need to know how it works by hand.
Predict, then reveal

Row is wrapped in memo, and there are 2,000 of them. Typing in the search box is slow. Why, and what's the smallest fix?

function Inbox({ messages }) {
  const [query, setQuery] = useState("");
  const [selected, setSelected] = useState(null);
  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      {messages.map((m) => (
        <Row key={m.id} message={m} onSelect={(id) => setSelected(id)} />
      ))}
    </>
  );
}

Every keystroke renders all 2,000 rows. setQuery renders Inbox, and onSelect={(id) => …} is a new function each time, so memo sees a changed prop on every row.

Smallest fix: onSelect={setSelected}. A state setter keeps the same identity for the component's whole life, so the prop never changes. The general fix is const onSelect = useCallback((id) => setSelected(id), []).

Staff-level answer: also move query and the input into their own component. The list then stops rendering on keystrokes, with no memo at all.

3 · useRef: a value that doesn't cause a render

useRef(initial) returns the same { current } object on every render. Changing .current does not render. Two uses (react.dev, useRef):

UseExample
A handle to a DOM node<input ref={inputRef} /> then inputRef.current.focus() in an effect or handler
A value handlers need but the screen doesn'tA timer ID, an AbortController, a WebSocket, the previous value

Rule: don't read or write ref.current during render. Do it in effects and event handlers. If the value has to appear on screen, it's state. In React 19, ref is a normal prop on function components, so forwardRef is no longer needed (React 19 post).

Predict, then reveal

You click the button three times. What does the screen show, and what does the console show?

function Clicks() {
  const count = useRef(0);
  return (
    <button onClick={() => { count.current++; console.log(count.current); }}>
      Clicked {count.current} times
    </button>
  );
}

The screen shows "Clicked 0 times". The console shows 1, 2, 3. The value changes, but nothing triggered a render, so the screen keeps the first render's output. It also reads .current during render, which breaks the rule. A value that's displayed belongs in useState.

4 · useEffectEvent: read the latest value without re-running the effect

An effect's dependency array decides when it re-runs. Sometimes the effect needs the latest value of something, but a change to that thing shouldn't restart it. useEffectEvent splits that read out:

const onKeyDown = useEffectEvent((e) => {
  if (e.key === "f" && selectedId) toggleFlag(selectedId);   // always the latest values
});
useEffect(() => {
  window.addEventListener("keydown", onKeyDown);
  return () => window.removeEventListener("keydown", onKeyDown);
}, []);   // subscribes once

Effect Events "always 'see' the latest values from render (like props and state) without re-synchronizing your Effect, so they're excluded from Effect dependencies" (react.dev, useEffectEvent; new in React 19.2). Its rules:

  • Call it only from inside effects, or from things an effect sets up such as listeners and timers. Never during render, and never pass it to children.
  • Never put it in a dependency array. Its identity changes on every render on purpose.
  • Don't use it to silence the lint rule. If a change to the value should restart the effect (a new room ID means a new connection), it's a dependency. React's docs: hiding dependencies "hides bugs".

5 · Cold check

Close the tables above, or scroll them out of view. Write first, then do the quiz.

From memory

Name the three things that make a component render. Say which one memo can block, and the one condition that has to hold for it to work.

1, its own state was set. 2, its parent rendered. 3, a context it reads changed. memo blocks only 2, and only if every prop is Object.is-equal to last time, which inline objects and functions break.

Q1 · memo

A child is wrapped in memo and gets onSave={handleSave}, where handleSave is a plain function declared in the parent. The parent renders. The child…

New object. The function is created again on each render, so Object.is fails. useCallback or React Compiler fixes it.
Q2 · useCallback

A function wrapped in useCallback is passed to a plain <button onClick>. What did useCallback buy you?

Nothing. A DOM element isn't a memo component, and no dependency array reads the function. The function is still created on every render; React just hands back the cached one.
Q3 · useRef

You store a WebSocket in useRef and replace it on reconnect. What happens on screen when ref.current changes?

Nothing. Exactly the right place for a socket: the handlers need it, the screen doesn't.
Q4 · useEffectEvent

An effect connects to roomId and shows a toast using theme. Changing the theme reconnects. The right fix is…

Split it. roomId should restart the connection, so it stays a dependency. theme is only read when the toast fires, so it goes in the effect event. Wrapping everything hides the real dependency.

Sentence to have ready: "A component renders when its state changes, when its parent renders, or when a context it reads changes. memo only skips the parent case, and only if every prop keeps its identity, which is what useMemo and useCallback are for. With React Compiler that's automatic. Without it, I'd first move state down or pass children before reaching for memo."
