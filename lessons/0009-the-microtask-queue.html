The microtask queue

What a promise is, when its callbacks run, and how errors travel down a chain. Then you write Promise.all, a timeout and a retry yourself.

Lesson 09 · JS fundamentals · ~40 min + 30 min drills · ← Lesson 8

1 · The mechanism: one thread, two queues

JavaScript runs on one thread. Anything that has to wait (a timer, a click, a network response) gets queued and runs later. There are two queues, and the event loop treats them differently. "During each iteration, it runs at most one pending JavaScript task, then any pending microtasks, then performs any needed rendering" (MDN, microtasks in depth).

QueueWhat goes in itHow much runs per loop
TaskThe script itself, setTimeout, setInterval, events (clicks, network callbacks)One
MicrotaskPromise callbacks (then/catch/finally), code after an await, queueMicrotaskAll of them, including any added while draining

So the loop is: run the current task to the end → drain every microtask → render → take the next task. "Microtasks can enqueue new microtasks and those new microtasks will execute before the next task begins." A setTimeout(fn, 0) therefore always comes after every promise callback that is already queued (MDN, Using promises: "Promise callbacks are handled as a microtask whereas setTimeout() callbacks are handled as task queues").

Predict, then reveal

Write the seven numbers in the order they print.

console.log("1");
setTimeout(() => console.log("2"), 0);
Promise.resolve().then(() => {
  console.log("3");
  setTimeout(() => console.log("4"), 0);
  queueMicrotask(() => console.log("5"));
});
queueMicrotask(() => console.log("6"));
console.log("7");

1 7 3 6 5 2 4 (run in Node 22).

  • The task (the script): prints 1 and 7. It queues timer 2, microtask 3 and microtask 6, in that order.
  • Drain the microtasks: 3 runs and queues timer 4 and microtask 5. Then 6. Then 5: it was added while draining, so it still runs before any task.
  • Next tasks: 2, then 4.

2 · A promise: three states, settled once

A promise is an object for a value that isn't there yet. It is pending, then either fulfilled (with a value) or rejected (with a reason). Fulfilled or rejected means settled, and it never changes after that: "Only the first call to resolveFunc or rejectFunc affects the promise's eventual state." The function you pass to new Promise runs synchronously; only the callbacks run later (MDN, Promise()).

then always returns a new promise. That is what makes a chain. How the new promise settles depends on what the callback does (MDN, Promise):

The callback…The next promise…
returns a valuefulfills with that value
returns a promisewaits for it and copies its result
throwsrejects with the error
doesn't exist for this state (no catch on a rejection)copies the previous result. An error skips every then until a catch

A catch that returns normally recovers the chain: the next then runs as if nothing failed. To keep it failed, rethrow. A callback that starts a promise and doesn't return it leaves that promise "floating": nothing waits for it and its error is lost (MDN, Using promises).

Predict, then reveal

What prints?

Promise.resolve(1)
  .then((x) => { console.log("a", x); throw new Error("boom"); })
  .then((x) => console.log("b", x))
  .catch((e) => { console.log("c", e.message); return 2; })
  .then((x) => console.log("d", x))
  .finally(() => console.log("e"));

a 1, c boom, d 2, e. The throw rejects the next promise, so b is skipped. The catch returns 2, which recovers the chain, so d gets 2. finally runs whatever the result and takes no argument.

Predict, then reveal

What prints, in order?

async function load(name) {
  console.log(name, "start");
  await null;
  console.log(name, "after await");
  return name;
}
console.log("before");
load("A").then((v) => console.log("done", v));
load("B");
console.log("after");

before, A start, B start, after, A after await, B after await, done A (run in Node 22).

Both calls run synchronously up to await, and each queues its continuation. after ends the task. Then the microtasks run: A resumes and returns, which queues the .then callback behind B's continuation, which was already waiting.

Sequential vs concurrent. await a(); await b(); starts b only after a finishes. If they don't depend on each other, start both and then wait: await Promise.all([a(), b()]). MDN: "it's always better to run promises concurrently … unless one promise's execution depends on another's result." Two independent 100 ms requests take 200 ms written the first way and 100 ms the second.

4 · The four combinators

Fulfills whenRejects whenUse it for
allall fulfill: values in input order, not finish orderany one rejects, with that first reasonEverything is required
allSettledall settle: {status, value} or {status, reason} eachnever, because of an inputShow what worked and what failed
racethe first to settle, either wayTimeouts
anythe first to fulfillall reject, with an AggregateErrorFastest mirror wins

Two traps. Promise.all rejecting "does not cancel the remaining operations": the other requests keep running, and stopping them takes an AbortController. Promise.all([]) fulfills straight away with [] (MDN, Promise.all, allSettled).

Q1 · combinators

A dashboard loads three widgets. Show each one that loaded, and an error in the slot of any that failed. Which call?

allSettled. It waits for every widget and tells you which failed. all with a catch loses the two that worked.
Q2 · all

Promise.all over three fetches. The second rejects at 20 ms. What happens to the other two?

They keep running. A promise is a result, not a handle on the work. Only an AbortController signal stops a fetch.
Q3 · any

All three promises passed to Promise.any reject. What does it reject with?

AggregateError, with the reasons in its errors array.
Q4 · await

const u = await getUser(); const p = await getPosts(); Each takes 100 ms and they don't depend on each other. How long, and the fix?

200 ms. The second request doesn't start until the first finishes. const [u, p] = await Promise.all([getUser(), getPosts()]).

5 · The React case: the spinner that drops

This is the bug from your async request layer rewrite (reference sheet). The ordering model it needs is the one above.

Predict, then reveal 
useEffect(() => {
  const c = new AbortController();
  setLoading(true);
  search(query, { signal: c.signal })
    .then(setResults)
    .catch(() => {})
    .finally(() => setLoading(false));
  return () => c.abort();
}, [query]);

The query goes from "a" to "ab" while "a" is still loading. List the three things that run, in order: the cleanup, the new effect, and the old request's finally. Is the spinner on or off while "ab" loads? What's the one-line fix?

1. Cleanup: abort() rejects the old request. Its callbacks are now queued as microtasks, but they can't run yet: React runs the cleanup and the new effect back to back, in one synchronous pass. 2. New effect: setLoading(true), and "ab" starts. 3. The task ends and the microtasks drain: the old catch, then the old finally calls setLoading(false).

The spinner is off while "ab" is still loading. The fix: .finally(() => { if (!c.signal.aborted) setLoading(false); }). Each effect's c is its own, so only the current request can clear the flag.

Do it

In exercises/0009-promise-drills/drills.mjs, write the four functions without using Promise.all, allSettled or any. Run node check.mjs in that folder after each one.

  1. sleep(ms): resolves after ms.
  2. promiseAll(items): behaves like Promise.all. Values in input order, the first rejection wins, [] fulfills with [], and plain values pass through.
  3. withTimeout(promise, ms): rejects with new Error("timeout") if promise hasn't settled within ms. Use Promise.race.
  4. retry(fn, attempts, delayMs): calls fn(), and on rejection waits delayMs and calls it again, up to attempts calls in total. It rejects with the last error.

7 · Cold check

From memory

State the event loop in one sentence. Then: what does a catch that returns a value do to the rest of the chain?

One task, then every microtask (including ones added while draining), then render, then the next task. Promise callbacks and code after await are microtasks; setTimeout and events are tasks.

It recovers the chain. The next then gets the returned value. Rethrow to keep it rejected.

Sentence to have ready: "Each turn of the event loop runs one task, then drains the whole microtask queue, then renders. Promise callbacks and anything after an await are microtasks, so they run before any setTimeout. A then returns a new promise; a throw skips ahead to the next catch, and a catch that returns recovers. For independent requests I start them all and await Promise.all, or allSettled when partial results are useful, and I remember that a rejection doesn't cancel the others."
