Which declaration wins

How the browser picks one value per property per element: matching, then the cascade, then inheritance if nothing matched. Then you predict the colour, five times.

Lesson 10 · CSS fundamentals · ~20 min · ← Lesson 9

1 · The mechanism: one question per element, per property

For every element and every property (say, the color of one <a>), the browser answers one question: which declaration applies? It works in this order:

StepWhat happens
1. MatchCollect every declaration whose selector matches this element. Rules that don't match are out, no matter how specific they are.
2. CascadeIf more than one matched, sort them: origin and !important (layers sit inside this step), then specificity, then order of appearance. The first one in the sorted list wins.
3. Inherit or defaultOnly when nothing matched. An inherited property (color, font-*) takes the parent's computed value. A non-inherited one (border, margin) takes its initial value.

The cascade and inheritance are separate mechanisms. The cascade chooses between declarations that target the element. Inheritance applies only when no declaration targets it (MDN, Inheritance: "inheritance controls what happens when no value is specified for a property on an element"). So an inherited value never competes in the cascade. Any rule that targets the element, even h1, beats it.

Matching: the space is a combinator

A space between two selectors is the descendant combinator. A B selects the B elements that have an A ancestor at any depth (MDN). No space makes a compound selector: "a set of simultaneous conditions on a single element" (MDN, Selector structure).

SelectorMatches
div.selectedA div that has class selected. One element, two conditions.
div .selectedAny element with class selected that is inside a div. Two elements.
div > .selectedThe same, but the div must be the direct parent.
Predict, then reveal

Both divs are direct children of body. Which of A, B and C turn red with div .selected? Which turn red with div.selected?

<div class="selected">A</div>
<div><span class="selected">B</span></div>
<div class="selected"><span class="selected">C</span></div>

div .selected: B and C, meaning the spans. The div holding A has no div ancestor, so it doesn't match. The span holding C matches because its parent is a div.

div.selected: the div holding A and the div holding C. The span inside C still shows red here, but only because color inherits from its red parent. That's step 3, not a match.

2 · Specificity: three columns, compared left to right

When matched declarations tie on origin and importance, specificity decides. It's a count in three columns, ID-CLASS-TYPE (MDN, Specificity):

ColumnCountsAdds 0
ID#nav*, combinators (  > + ~), :where(…)
CLASS.link, [type="radio"], pseudo-classes such as :hover and :nth-child()
TYPEa, h1, pseudo-elements such as ::before

Compare left to right. The first column that differs decides. "The selector with the greater value in the ID column wins no matter what the values are in the other columns." 1-0-0 beats 0-15-0. It is not a sum. If all three columns are equal, the later declaration wins. How close an element is in the DOM tree has no effect: MDN says "the proximity of an element to other elements that are referenced in a given selector has no impact on specificity."

Three special cases:

  • :is(), :not(), :has() add nothing themselves. They take the specificity of their most specific argument, so :is(#a, .b) counts as 1-0-0.
  • :where() is always 0-0-0, whatever is inside it. Libraries use it so their defaults are easy to override.
  • An inline style attribute beats every selector (think 1-0-0-0). Only !important overrides it.

Every drill below uses this markup:

<ul id="nav" class="menu">
  <li><a class="link" href="/">Home</a></li>
</ul>
Drill 1 · Colour of Home?

Write each tuple, then the winner.

.menu li .link { color: green; }
#nav a         { color: blue; }
a.link         { color: red; }

Blue. The tuples are 0-2-1, 1-0-1 and 0-1-1. The ID column differs first, so #nav a wins. Its order in the file doesn't matter.

Drill 2 · Colour of Home? 
.menu .link       { color: green; }
ul li a.link      { color: red; }

Green. The tuples are 0-2-0 and 0-1-3. The ID columns tie, so the CLASS column decides: 2 beats 1. Three type selectors can't make up for a missing class. Red being declared later doesn't matter, because order only breaks a full tie.

Drill 3 · Colour of Home? 
:is(#nav, .menu) a    { color: blue; }
:where(#nav) a.link   { color: red; }

Blue. :is() takes its most specific argument, #nav, so the first rule is 1-0-1. :where() counts as zero, so the second is 0-1-1, from a.link alone.

3 · Inheritance loses to anything that targets the element

MDN: "Styles for a directly targeted element will always take precedence over inherited styles, regardless of the specificity of the inherited rule."

Drill 4 · Colours of the h2 and the p? Does the p get a border? 
<section id="card" class="card">
  <h2>Title</h2>
  <p>Body</p>
</section>

#card.card { color: green; border: 1px solid; }
h2         { color: purple; }

h2 purple. p green. No border on the p.

  • #card.card (1-1-0) matches the section, not the h2. For the h2, only h2 matches, so there is nothing to compare: it wins and the colour is purple. The 1-1-0 never competes.
  • No rule matches the p, so step 3 applies. color inherits, so the p is green.
  • border doesn't inherit, so the p gets the initial value, none.

4 · Above specificity: importance, origin and layers

Specificity only decides among declarations that already tie on the steps above it. The full order (MDN, Introduction to the cascade):

  1. Origin and importance. For normal declarations, author CSS beats the user's, which beats the browser's. !important reverses that order: browser !important beats user !important, which beats author !important, and every !important beats every normal declaration.
  2. Layers (@layer), still inside step 1. For normal declarations, later layers beat earlier ones, and unlayered CSS beats every layer, regardless of specificity. For !important the order reverses again: the first layer wins, and unlayered CSS loses.
  3. Specificity.
  4. Order of appearance: the last one wins.
Drill 5 · Two separate cases. Colour of Home in each? 
/* (a) */
@layer base { #nav a { color: red; } }
a { color: blue; }

/* (b) — the a has style="color: orange" */
.link { color: green !important; }

(a) Blue. Unlayered normal CSS beats layered normal CSS before specificity is ever compared, so the 1-0-1 inside the layer loses to a plain a. This is why putting a library's or reset's CSS in a layer makes it easy to override.

(b) Green. An inline style beats every selector, but !important beats any normal declaration, and the inline style is normal.

5 · Retrieval check

Without scrolling up

(1) What's the difference between p.note and p .note? (2) Give the tuples for #app .card:hover > h2::before and :where(.x) ul li. (3) A rule #main { color: red } and an element inside #main with a p { color: blue } rule. What colour, and is that the cascade or inheritance?

(1) p.note is a p that has the class. p .note is a .note element inside a p.

(2) 1-2-2: #app, then .card and :hover, then h2 and ::before. 0-0-2: :where adds zero, leaving ul and li.

(3) Blue, and it's the cascade. p matches the element directly. #main matches only the ancestor, so its red would reach the p only through inheritance, and inheritance applies only when nothing targets the element.

Sentence to have ready: "For each element and property, the browser collects the declarations whose selectors match. The cascade sorts them by origin and importance, then layers, then specificity, then source order. Specificity is an ID-class-type count compared column by column, so one ID beats any number of classes. :where is zero and :is takes its most specific argument. Inheritance only kicks in when nothing matched the element, so a bare h1 rule beats a color inherited from an ID-styled parent. In practice I keep specificity flat with single classes, and use layers or :where for defaults that should be easy to override."
