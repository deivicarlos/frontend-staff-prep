The request pipeline

Every cross-origin request goes through the same four stops: is it sent, which cookies go with it, what the server does, and whether the script may read the answer. Learn the four stops, then trace eight requests through them.

Lesson 11 · Security track S1 · ~35 min · have a timer ready · ← Lesson 10

Cold, 2 minutes, before reading

You're logged in to bank.com. You open evil.com, which runs fetch("https://bank.com/api/balance", { credentials: "include" }). Say step by step what the browser and the server do, and whether evil.com ends up with your balance.

1 · What a request is, and why cookies exist

HTTP is text. The client sends a request: a method, a URL, headers, and an optional body. The server answers with a response: a status, headers, and a body. The server keeps no memory between requests, so every request has to say who it's from on its own. A cookie is how a browser does that.

POST /api/cart HTTP/1.1
Host: api.shop.com
Origin: https://app.shop.com      ← browser: who started it
Sec-Fetch-Site: same-site         ← browser: same site?
Cookie: sid=8f3a…                 ← browser: from the jar
Content-Type: application/json

{"item": 42}

HTTP/1.1 201 Created
Access-Control-Allow-Origin: https://app.shop.com
Set-Cookie: sid=8f3a…; HttpOnly; Secure; SameSite=Lax

Your code doesn't write the three marked headers. The browser adds them, and scripts can't fake Origin or Sec-Fetch-Site (MDN: forbidden headers). That's why the server can trust them as a statement about the browser.

The cookie jar

Set-Cookie puts a name, a value and some rules into the browser's jar. Before every request, the browser checks each cookie on its own against the request's destination and joins the cookies that pass into one Cookie: header. Which page started the request doesn't change which jar is used. It is only checked by SameSite, in section 3.

RuleThe cookie goes only if…
DomainIf it's left out, the destination host is exactly the one that set it ("host-only"). Domain=shop.com also covers every subdomain. It can't be a public suffix such as com or github.io.
PathThe URL path starts with it. MDN: Path "is not intended as a security measure".
SecureThe request is https: (localhost is exempt).
Expires / Max-AgeIt hasn't expired.
SameSiteThe initiator passes the site test. This is the only rule that looks at who started the request. See section 3.
HttpOnlyNot a sending rule. It hides the cookie from document.cookie. MDN: it "will still be sent with JavaScript-initiated requests".
Apply, 3 minutes

https://shop.com responds with Set-Cookie: sid=abc; Path=/api; Secure; HttpOnly (no Domain). All of these requests start on a shop.com page. For each one, write sent or not sent and the rule that decides it.
(1) GET https://shop.com/api/cart
(2) GET https://shop.com/account
(3) GET http://shop.com/api/cart
(4) GET https://api.shop.com/api/cart
(5) console.log(document.cookie), followed by fetch("/api/cart").
(6) The server adds Domain=shop.com. Which of your answers changes?

(1) Sent. Every rule passes. (2) Not sent, because of Path. (3) Not sent, because of Secure. (4) Not sent: there's no Domain, so it's host-only and api.shop.com is a different host. (5) sid isn't in the log (HttpOnly), and the fetch sends it anyway. HttpOnly hides it from your code, not from the request. (6) (4) changes to sent. Domain extends the cookie to every subdomain.

2 · Origin and site: two different "same" tests

OriginSite
Made ofScheme + host + portScheme + registrable domain (a public suffix plus one label in front). The port is ignored
app.shop.com vs api.shop.comDifferentSame (shop.com)
Used byThe same-origin policy, CORS, fetch's default credentialsSameSite cookies, Sec-Fetch-Site

SameSite compares sites including the scheme, so http://shop.com and https://shop.com are cross-site (MDN, Site: "schemeful same-site").

Apply, 2 minutes

For each pair, write same-origin, cross-origin but same-site, or cross-site. Pairs 1 to 5 are all compared with https://app.shop.com.
(1) https://app.shop.com/admin
(2) https://app.shop.com:8443
(3) https://api.shop.com
(4) http://app.shop.com
(5) https://shop.co.uk
(6) https://alice.github.io vs https://bob.github.io

(1) Same-origin: only the path differs. (2) Cross-origin, same-site: the port changes the origin but not the site. (3) Cross-origin, same-site. (4) Cross-site: the scheme differs, and SameSite uses schemeful site. (5) Cross-site. (6) Cross-site: github.io is a public suffix, so each user's subdomain is its own site. That's the reason a site's cookies can't use Domain=github.io.

3 · The pipeline: four stops

On 10-14 you learned two gates. The full picture adds the server and a read check after it. The same-origin policy (SOP) is the browser's default rule: a page may send cross-origin (links, form submits) and embed (img, script), but its scripts may not read cross-origin responses (MDN, SOP). CORS is the server's way of relaxing that rule for specific origins.

StopQuestionWho decides, by what
Gate 1Is the request sent? Navigations and embeds (link, form submit, <img>) are always sent. For a script request to another origin, it depends on whether the request is simple:
· Simple (GET/HEAD/POST, only safelisted headers, Content-Type one of application/x-www-form-urlencoded, multipart/form-data, text/plain): sent, with no question asked.
· Anything else (a JSON body, PUT/DELETE, any other header, Authorization included): an OPTIONS preflight goes first, without cookies. If the server's answer doesn't approve this origin, method and headers, the real request is never sent.
Gate 2Which cookies go? The jar rules from section 1, for each cookie, plus two more:
· SameSite compares the initiator's site with the destination's. Strict: same-site only. Lax: also cross-site top-level navigations with a safe method (clicking a link). None: always, and requires Secure.
· fetch's credentials defaults to same-origin, so a cross-origin fetch sends no cookies unless it sets credentials: "include".
ServerWhat happens? The request runs. Auth middleware checks for a session: none means 401, the wrong user means 403/404. Side effects happen here, before the browser decides anything about reading. The browser never blocks a request because a cookie is missing. The server rejects it.
Gate 3May the script read the response? Only if Access-Control-Allow-Origin matches the calling origin. For a request sent with credentials, the response also needs Access-Control-Allow-Credentials: true, and * isn't accepted. If the check fails, the script gets a network error with no detail, but the server has already done the work.

Why preflight exists. Forms and links could always send GET, and POST with a form or text body. Servers already had to survive those. fetch gave scripts new powers (a JSON body, DELETE, custom headers), so the browser asks first before using them against a server that never opted in. MDN: "the server doesn't have to opt-in … to receive any request that looks like a form submission."

CORS protects the user's browser, not your server. It decides what another site's scripts can do with your users' cookies. curl has no gates at all. Only the server's own checks stop it.

Trace it

The same setup holds for every scenario in this section. You're logged in to app.shop.com. The API is api.shop.com, which set sid=…; HttpOnly; Secure; SameSite=Lax; Path=/ (no Domain). The API's CORS policy allows origin https://app.shop.com with credentials, methods GET/POST/DELETE, and header Content-Type. Answer all four stops for each scenario: sent? · cookie? · what the server does · readable?

Trace, 5 minutes

A. On app.shop.com: fetch("https://api.shop.com/cart", { credentials: "include" })
B. The same, but without the credentials option.
C. On evil.com: fetch("https://api.shop.com/cart", { credentials: "include" })
D. On evil.com: fetch("https://api.shop.com/cart/items/7", { method: "DELETE", credentials: "include" })

A. Sent: it's a simple GET. Cookie: yes, because the call is same-site and Lax allows it, and include is set. The server returns the cart. Readable: yes, ACAO matches and ACAC is true. This is the normal app path.

B. Sent. Cookie: no. It's cross-origin, and the default same-origin mode leaves cookies off. The server returns 401. Readable: yes, the script reads a 401. This is the most common real bug: "the API says I'm logged out on every call."

C. Sent: it's a simple GET, so gate 1 doesn't apply. Cookie: no. It's cross-site and not a top-level navigation, so Lax keeps it home. The server returns 401. Readable: no, ACAO doesn't match evil.com. Two separate stops each protect you. Check your cold answer: did you say the request goes out?

D. DELETE isn't simple, so an OPTIONS preflight goes first, with no cookie. The server's policy doesn't list evil.com, so the DELETE is never sent. Cookie, server and read don't apply.

Trace, 5 minutes

E. evil.com auto-submits <form method="POST" action="https://api.shop.com/cart/clear">.
F. A stored XSS runs inside app.shop.com and calls fetch("https://api.shop.com/cart/items/7", { method: "DELETE", credentials: "include" }).
G. An attacker who copied the sid value out of a log runs curl -X DELETE https://api.shop.com/cart/items/7 -H "Cookie: sid=…".
H. Two mistakes ship together. The API now copies any request's Origin into Access-Control-Allow-Origin with Allow-Credentials: true, and sid becomes SameSite=None; Secure for a partner widget. Run scenario C again, in Chrome.

E. Sent: a form submit is a navigation, so there's no preflight. Cookie: no. A cross-site POST isn't Lax's exception. The server returns 401, and nothing is cleared. SameSite is the stop that saved you here.

F. The preflight's Origin is app.shop.com, so it's approved and the request is sent. Cookie: yes, it's same-site. The server deletes the item. Readable: yes. Every stop passes, because to the browser this script is your app. HttpOnly changes nothing. No gate stops XSS. That's lesson S3.

G. It succeeds. curl isn't a browser, so there's no preflight, no SameSite and no CORS. The server sees a valid session. CORS never protected the server. Only server-side controls do: short sessions, binding the session to a device, detecting anomalies.

H. Sent (simple GET). Cookie: yes. With None, the cookie goes cross-site, and Chrome still sends third-party cookies. The server returns your cart. Readable: yes, because the reflected ACAO matches evil.com and ACAC is true. evil.com reads your data. Either mistake alone stays blocked, because gates 2 and 3 are independent. Ship both and you have a full breach. The fix is an explicit allowlist of origins, never reflection.

4 · Why public APIs take a header token, not a cookie

A cookie is an ambient credential: the browser attaches it to any request that passes gate 2, whoever started it. That's what CSRF exploits. An Authorization: Bearer … header is attached only by code that holds the token.

Session cookieBearer token in a header
Attached byThe browser, automaticallyYour code, deliberately
CSRF exposureYes. Needs SameSite and a CSRF defenceNone. Another site can't make the browser add it
ClientsBrowsers, on your own site(s)Any: other origins, mobile apps, servers, curl
Gate 1Simple requests skip the preflightAuthorization isn't safelisted, so every call is preflighted
XSSHttpOnly: the script can use the session in the tab, but can't take it awayThe token is reachable from JS, so it can be stolen and used anywhere until it expires
Apply, 3 minutes

You run api.acme.com. Customers call it from SPAs on their own domains (app.customer1.com, …), and from their backends. A teammate proposes the session cookie your own dashboard uses, set to SameSite=None. Write your answer: what you'd use instead, and what the CORS policy has to say.

A token in the Authorization header. A SameSite=None cookie works from every site on the web, including evil ones, so it's CSRF exposure on every endpoint. It also does nothing for backend callers, which have no cookie jar.

CORS: answer the preflight with each customer's origin, taken from an allowlist, and allow the Authorization header. You don't need Allow-Credentials, because no cookies are involved. Since a header token can't be forged cross-site, Allow-Origin: * is even acceptable for a truly public, token-only API. The token's own weakness is XSS on the customer's side, which is why those tokens are short-lived and scoped. That's S4.

5 · Retrieval check (cold, 8 minutes)

Scroll so nothing above is on screen. This is lesson 6's drill (2/5 on 10-07). The target is 4/5, and each point needs a correct verdict and the rule that decides it.

Without scrolling up

A BFF session cookie is set as sid=…; HttpOnly; Secure; SameSite=Lax; Path=/ on app.example.com, with no other CSRF defence. For each attack, write succeeds or blocked, and name the stop and rule that decide it.
(1) evil.com auto-submits a form POST to /api/projects/42/delete.
(2) The API also accepts GET /api/projects/42/delete, and evil.com shows a link to it that the user clicks.
(3) The same GET URL, but as <img src> on evil.com.
(4) A stored XSS on blog.example.com (another team's app) auto-submits the form POST from (1).
(5) A stored XSS inside app.example.com runs fetch("/api/projects/42", { method: "DELETE" }).
(6) One sentence: "We have CORS locked down, so our API is protected." What's wrong with it?

(1) Blocked at gate 2. It's a cross-site POST, which isn't Lax's exception, so the cookie stays home. The server returns 401.

(2) Succeeds. A link click is a top-level navigation with a safe method, which is exactly Lax's exception. The bug is a GET that changes state.

(3) Blocked at gate 2. An <img> is a subresource load, not a top-level navigation.

(4) Succeeds. blog.example.com and app.example.com are the same site, so SameSite never applies. Fetch Metadata that accepts only same-origin, or a CSRF token, would stop it.

(5) Succeeds. It's same-origin, so every stop passes. HttpOnly doesn't stop the cookie from being sent.

(6) CORS limits what other sites' scripts in your users' browsers can do. It doesn't stop simple requests from being sent, and it does nothing against curl, a stolen session, or XSS in your own origin. The server is protected only by its own authN and authZ.

Sentence to have ready: "A cross-origin request passes four stops. The browser decides whether it's sent: simple requests always go, anything else waits for a preflight. Then it decides which cookies go: Domain, Path and Secure by destination, SameSite by who started it, and fetch only sends them cross-origin with credentials include. Then the server runs it. Last, CORS decides whether the calling script may read the response. HttpOnly is in none of those. So CORS protects users' browsers from other sites. It never protects the server, which needs its own authentication and authorization."

Ask me. Paste the cold answer, the two traces (A–H) and the retrieval check exactly as first written. If a reveal surprised you, name the stop you skipped.
