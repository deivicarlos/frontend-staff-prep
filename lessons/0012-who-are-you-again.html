Who are you, again?

Logging in proves who you are once. After that, a random session ID stands in for you on every request. Learn how each half works: how the password is stored, and how the session ID is issued, checked and killed. Each choice exists to stop one specific attack.

Lesson 12 · Security track S2 · ~35 min · have a timer ready · ← Lesson 11

Warm-up from S1, 2 minutes

evil.com shows a link to https://app.example.com/api/projects/42/delete (a GET), and the user clicks it. In two sentences: does CORS take part in this request? Who sees the response?

No. A clicked link is a navigation, not a script request, so CORS never runs. The response loads in the tab and the user sees it. CORS only decides whether a script may read a cross-origin response.

Cold, 3 minutes, before reading

You're building login for a Node server from scratch. (a) What do you write in the users table for the password? (b) After a correct password, what does the server send back, and what does it keep? (c) What does logout do, on the server and in the browser?

Locked. Sections 2–3 answer each part. Compare when you get there.

1 · The mechanism: one proof, then a stand-in

HTTP is stateless: the server keeps no memory between requests (lesson 11, §1). Checking a password on every request would be slow, and it would mean keeping the password in the browser. So authentication is split into two moments:

MomentWhat happensThe secret being checked
Login, onceThe user sends a password (or signs a challenge with a passkey). The server checks it, creates a session, and sends its ID back in Set-Cookie.The password
Every request afterThe browser attaches the cookie (lesson 11's stop 2). The server looks the ID up in its session store and finds the user.The session ID

Where each thing lives:

PlaceHoldsNever holds
Users tableUser ID, email, a password hashThe password
Session store (Redis, a DB table)Session ID → { user ID, created at, last seen }The password
Browser cookieThe session ID, nothing elseUser data, the password

The consequence that drives the rest of the lesson: after login, the session ID is the credential. Anyone who presents it is that user, and the server can't tell them apart. It's a bearer secret. Every session rule below protects that ID. express-session works exactly this way: "Session data is not saved in the cookie itself, just the session ID."

Apply, 2 minutes

(1) An attacker copies your session cookie value out of a shared laptop's browser. They don't know your password. Can they act as you? (2) You change your password. Should the server do anything to your existing sessions? (3) Why don't we just put userId=42 in the cookie?

(1) Yes. After login the ID is the credential. The password isn't checked again.

(2) Yes, kill them. Otherwise a session the attacker already holds outlives the reset. A password change is a privilege-level change, and OWASP says to renew the session ID after one.

(3) The client controls the cookie, so anyone could write userId=43. A session ID is random and only means something because the server looks it up.

2 · Storing the password

Assume the users table will leak. The question is what the attacker can do with it.

You storeAttacker with the dumpVerdict
PlaintextLogs in as everyone, and tries the same passwords on other sites.Never
EncryptedSteals the key from the same server, then decrypts. Encryption is reversible by design.Never for passwords
Fast hash, e.g. sha256(pw)Hashes billions of guesses offline. Identical passwords give identical hashes, and precomputed tables work.Broken
Fast hash + per-user saltPrecomputed tables die, but each guess is still cheap.Not enough
Slow, salted hash (Argon2id)Each guess costs real time and memory, so cracking is slow, per user.Do this

The three ideas, per the OWASP Password Storage Cheat Sheet:

  • Hash, don't encrypt. A hash is one-way. At login, hash the attempt and compare.
  • Salt: a unique random value per password, stored next to the hash. It "forces attackers to crack each hash individually." Argon2id and bcrypt generate it for you and put it inside the output string.
  • Slow on purpose (the work factor). Pick, in order: Argon2id (minimum m=19 MiB, t=2, p=1); scrypt if that's unavailable; bcrypt for legacy systems only (cost ≥10, and its input stops at 72 bytes); PBKDF2-HMAC-SHA256 at 600,000 iterations when FIPS-140 compliance is required. Rule of thumb: hashing should take under a second. Make it too slow and login becomes a way to exhaust your server's CPU.

A pepper is an optional secret shared by every password and kept outside the database (in a secrets manager), so a DB-only leak isn't enough to crack anything.

What you're allowed to demand of the password itself has changed. NIST SP 800-63B-4: at least 15 characters when the password is the only factor, or 8 if it's part of MFA. Accept at least 64. No composition rules (no "one symbol, one digit"), no forced periodic changes, but force a change on evidence of compromise. Do check new passwords against a blocklist of common and breached ones.

Apply, 3 minutes

A legacy app stores sha256(password), with no salt. The table leaks. (1) Why do 4,000 users share the same hash, and what does the attacker learn from that? (2) You add a random per-user salt but keep SHA-256. What did that fix, and what didn't it fix? (3) How do you move existing users to Argon2id without knowing their passwords?

(1) Same input, same hash: they all chose the same password (probably 123456). Crack it once and you have 4,000 accounts. Precomputed tables crack the common ones instantly.

(2) Fixed: identical passwords now hash differently, and precomputed tables are useless. Not fixed: SHA-256 is built to be fast, so guessing each user's password is still cheap.

(3) On each user's next successful login you have the plaintext for a moment: verify it against the old hash, rehash it with Argon2id, store the new hash. To protect everyone else right away, wrap the old hashes now: argon2id(sha256(pw)), and replace each with a direct hash at that user's next login. Or expire long-inactive accounts and force a reset. These are the methods in OWASP's "Upgrading Legacy Hashes".

3 · The session: issue it, check it, kill it

The ID is the credential, so each rule closes one way of getting or keeping someone else's ID. All of these come from the OWASP Session Management Cheat Sheet.

RuleAttack it stops
The ID comes from a CSPRNG, with ≥64 bits of entropy. No user IDs, no timestamps.Guessing. The attacker enumerates IDs until one works.
Issue a new ID at login, and on any privilege change (password change, role change). In express-session: req.session.regenerate().Session fixation. The attacker gets a pre-login ID, plants it in your browser, and waits for you to log in. If the ID survives login, they now hold a logged-in session.
The server enforces an idle timeout (15–30 min for low risk, 2–5 for high value) and an absolute timeout (e.g. 4–8 h for an office workday). The cookie's expiry is a hint, not enforcement.A stolen or abandoned ID that lives forever. Client-side timers can be edited, so they don't count.
Logout deletes the session on the server (req.session.destroy()), then clears the cookie.A copied ID still working after "logout". Clearing only the cookie removes your copy and leaves the attacker's valid.
Cookie: __Host- prefix, HttpOnly, Secure, SameSite=Strict or Lax.Theft by script (HttpOnly), sending over plain HTTP (Secure), subdomain overwrite (__Host-, lesson 11), CSRF as defence in depth (SameSite, S3).
A real store (Redis, a DB), not express-session's default MemoryStore.Not an attack: MemoryStore "is not designed for a production environment". It leaks memory and doesn't scale past one process.

Fixation, step by step, because it's the one people can't reconstruct:

1. Attacker visits app.com            → gets sid=AAA (anonymous)
2. Attacker gets sid=AAA into your browser (e.g. a subdomain sets the cookie)
3. You log in. Server marks session AAA as "user 42"
4. Attacker sends Cookie: sid=AAA     → is user 42
   Fix: at step 3 the server issues sid=BBB and deletes AAA. The attacker's AAA is dead.
Apply, 4 minutes. Name the rule broken and the attack, or say "fine"

(1) Logout runs res.clearCookie("sid") and returns 200.
(2) Login sets req.session.userId = user.id on the existing session and saves it.
(3) Session IDs are `${userId}-${Date.now()}`.
(4) The SPA logs the user out after 30 idle minutes with a setTimeout; the server's session never expires.
(5) Login calls regenerate(), the session lives in Redis with a 30-minute idle and 8-hour absolute timeout, and logout calls destroy().

(1) Broken: logout must invalidate on the server. A copied ID still works.

(2) Broken: no new ID at login, so it's open to session fixation.

(3) Broken: guessable, nowhere near 64 random bits. Anyone who knows a user ID and roughly when they logged in can guess it.

(4) Broken: the timeout is client-side. A stolen ID never expires, because the attacker doesn't run your SPA.

(5) Fine.

4 · A second factor, and why passkeys are different

A password is a secret the user types, so a convincing fake page can collect it. A one-time code from an app or an SMS is also typed, so the fake page collects that too and relays both to the real site within seconds. NIST: "Passwords are not phishing-resistant", and OTP and out-of-band authenticators "SHALL NOT be considered phishing-resistant" (SP 800-63B-4). Phishing resistance needs cryptographic authentication.

A passkey is a WebAuthn credential. Nothing is typed:

StepWhat happens
RegisterThe device makes a key pair for this site (the relying party ID, e.g. example.com). The server stores only the public key.
Log inThe server sends a random challenge. The device signs it with the private key, which never leaves the device. The server checks the signature with the stored public key, and checks the challenge and the origin.

Two consequences. Phishing fails: the browser ties the credential to the site's origin, so a fake examp1e.com can't get a signature that example.com will accept ("the signature changes with the origin of the website", MDN). And a server breach leaks only public keys, which can't be used to log in. After a passkey login, everything in §3 still applies: the server still issues a session ID.

Apply, 2 minutes

A phishing page proxies everything you type to the real site in real time. Say what the attacker ends up with when you use (1) password only, (2) password + authenticator-app code, (3) a passkey.

(1) Your password, which they can use whenever they like.

(2) A logged-in session. They relay the code within its 30-second window, and the real site hands them the session ID. The code only raised the bar against stolen password lists.

(3) Nothing. The browser won't use the real site's credential on the phishing origin, and a signature it produced for the fake origin fails the real server's origin check.

Retrieval check · 5 minutes, cold, no scrolling

Without scrolling up

Say it out loud first, then write it. An interviewer asks: "Walk me through authentication for a web app with server sessions, and what each choice protects against." Cover: (1) what's stored for the password and why each property; (2) what the browser holds after login, and why that's the thing to protect; (3) three session rules, each with the attack it stops; (4) why a passkey beats password + OTP.

(1) A slow, salted, one-way hash (Argon2id). One-way, so a leak doesn't give back passwords. Salted, so equal passwords differ and precomputed tables don't work. Slow, so offline guessing is expensive per user.

(2) Only a random session ID in an HttpOnly, Secure cookie. After login the ID is the credential: whoever presents it is the user.

(3) Any three: ≥64-bit CSPRNG IDs (guessing); new ID at login (fixation); server-enforced idle and absolute timeouts (a stolen ID living forever); logout destroys the server session (a copied ID outliving logout).

(4) The private key never leaves the device and its signature is bound to the real origin, so a phishing page gets nothing usable. A typed code can be relayed in real time.

Sentence to have ready: "Login proves identity once. After that, a random session ID in an HttpOnly, Secure cookie stands in for the user, so that ID is the credential. Passwords are stored as Argon2id hashes, salted and deliberately slow, because the table will leak someday. The ID is regenerated at login against fixation, timed out on the server, and destroyed on the server at logout. If I want phishing resistance I add passkeys, because the signature is bound to the origin and nothing typed can be relayed."

Ask me. Paste the cold answer from the top and the retrieval check, exactly as first written. Then say §3's fixation trace back to me in your own words.
