The browser works for anyone

Once you're logged in, your browser holds the credential and attaches it to every request that goes to your app. Two attacks use that without ever seeing the credential: CSRF gets your browser to send a request, and XSS gets code running inside your page. Learn the browser behaviour each one uses, and the defence that takes it away.

Warm-up from S1 and S2, 3 minutes

(1) evil.com has a hidden <form method="POST" action="https://app.example.com/transfer"> and calls form.submit(). Does CORS run? Does the request reach the server? (2) In one line: in session fixation, what does the attacker already hold before you log in, and what does the server change at login to stop it?

(1) No CORS: form.submit() is a navigation, not a script request. The request reaches the server. Whether it arrives logged in depends only on whether the browser attaches the cookie.

(2) The attacker holds the session ID they planted in your browser. At login the server issues a new ID and deletes the old one, so the ID the attacker holds never becomes logged in.

Your app keeps the login in an HttpOnly session cookie. Without knowing the password or the session ID, describe two different ways an attacker can get your server to act as the logged-in user.

Locked. Sections 2 and 3 are the two ways. Compare when you get there.

1 · The mechanism: two things the browser does for you

Lesson 12 ended with this: after login, the session ID is the credential, and it lives in a cookie. The browser handles that cookie on its own, through two behaviours:

The browser…Which meansThe attack that uses it
A. attaches a cookie based on where the request goes, not which page started it (lesson 11, stop 2) Any page on the internet can make your logged-in browser send a request to your app, and the cookie goes with it. CSRF (cross-site request forgery): the attacker's page sends the request.
B. gives every script in a page that page's full powers: read the DOM, send same-origin requests with cookies, read the responses Whoever gets a script into your page can do anything your own code can. XSS (cross-site scripting): the attacker's code runs inside your page.

Neither attack needs the session ID itself. That's why HttpOnly, which only stops scripts from reading the cookie, isn't a defence against either one. MDN: an HttpOnly cookie "will still be sent with JavaScript-initiated requests" (Set-Cookie).

CSRFXSS
Attacker's code runsOn their own siteInside your origin
Can send requests as the userYes, the kinds a page may send without permission (form, link, image, simple fetch)Yes, any request your own code could send
Can read your responsesNo. The same-origin policy blocks the read, but the action already happenedYes
Relies onCookie-based auth (behaviour A)Your app running attacker data as code (behaviour B)

Phishing (lesson 12, §4) is the third industry-standard attack, and it's different: there, the attacker gets the user to hand over the credential itself.

Apply, 2 minutes. CSRF, XSS or neither, and what the attacker gets

The user is logged in to app.example.com.
(1) A comment saved as <img src=x onerror="fetch('/api/transfer', …)"> is shown as HTML to everyone who opens the thread.
(2) evil.com contains <img src="https://app.example.com/api/logout">, and logout is a GET.
(3) evil.com runs fetch("https://app.example.com/api/me", { credentials: "include" }) to read the user's email. The app sends no CORS headers.
(4) The search page writes ?q= into the HTML unescaped, and the attacker emails the user a search link.

(1) XSS. The attacker's code runs inside your page for every reader, and its fetch goes out with the cookie.

(2) CSRF. The browser loads the image, attaches the cookie (if SameSite lets it, §2), and the server logs the user out. The attacker never sees the response and doesn't need to.

(3) Neither. The request is sent, but it's a script request, so CORS applies: with no Access-Control-Allow-Origin, the browser won't hand the response to evil.com's script. Reading data across origins is what the same-origin policy stops. CSRF is about actions, not reads.

(4) XSS. The link carries the script, the server echoes it into the page, and it runs in your origin.

2 · CSRF: what the forged request needs

For a forged request to work, three things must be true. Each defence takes one away:

The attacker needsDefence that removes itHow
The browser to attach the cookie to a request from their site SameSite=Lax or Strict on the cookie Strict: cookie only on requests started from the same site. Lax: same, plus cross-site top-level navigations with a safe method (a link click, location change, or GET form). Cross-site POSTs, fetch, <img> and iframes get no cookie.
A request the browser sends without asking the server first Require a custom header, e.g. X-CSRF-Token A page can't add a custom header with a form or link. A script can, but then the browser sends a preflight, and your CORS policy only lets your own origins through.
To know every value in the request A CSRF token The server puts a random secret, tied to the session, in the page (hidden field or JSON, "should not be transmitted in a cookie") and checks it on every state-changing request. The attacker can't read your page, so they can't know it.
The server not to check who started the request Fetch Metadata The browser adds Sec-Fetch-Site (same-origin, same-site, cross-site, none). The server rejects POST/PUT/PATCH/DELETE marked cross-site. Fall back to checking Origin for old browsers.

Three rules from the OWASP CSRF Prevention Cheat Sheet that the table doesn't show:

  • "Do not use GET requests for state changing operations." Lax sends the cookie on a cross-site link click, so a state-changing GET is reachable by anyone who can show the user a link.
  • SameSite is defence in depth, not the defence. Two reasons. "Same site" means the same registrable domain (MDN, Site), so blog.example.com and app.example.com are the same site, and SameSite does nothing between them. And when SameSite is left unset, only "some browsers" default to Lax, and that default still sends the cookie on cross-site POSTs for two minutes after it was set (MDN). Set it explicitly, and add a token or Fetch Metadata.
  • "Cross-Site Scripting (XSS) can defeat all CSRF mitigation techniques!" Code inside your page can read the token, add the header, and is same-origin. That's §3.
Apply, 4 minutes. Succeeds or blocked, and what decides it

The session cookie on app.example.com is sid=…; HttpOnly; Secure; SameSite=Lax; Path=/. There's no other CSRF defence. For each attack, say whether it succeeds and what the browser or server does that decides it.
(1) evil.com calls form.submit() on a POST form to /api/transfer.
(2) The API also deletes a project on GET /api/projects/42/delete, and evil.com shows a link to it that the user clicks.
(3) The same GET URL, in an <img src> on evil.com.
(4) A stored XSS on blog.example.com (another team's app) submits the POST form from (1).
(5) You add Fetch Metadata to the server, rejecting state-changing requests marked cross-site or same-site. Replay (4).

(1) Blocked. A cross-site POST isn't a safe method, so Lax keeps the cookie home. The request arrives without a session.

(2) Succeeds. A link click is a top-level navigation with GET, exactly what Lax still allows. The bug is the state-changing GET.

(3) Blocked. An image load is a subresource request, not a top-level navigation, so Lax withholds the cookie.

(4) Succeeds. blog.example.com and app.example.com share a registrable domain, so the request is same-site and Lax sends the cookie.

(5) Blocked. The browser marks the request Sec-Fetch-Site: same-site, and the server refuses it. (A CSRF token would also stop it: the blog's script can't read app.example.com's page.)

Score the mechanism, not the verdict alone.

3 · XSS: the app runs attacker data as code

XSS happens when attacker-controlled text ends up somewhere the browser treats as code. The three kinds differ only in where the payload sits (OWASP, XSS):

KindWhere the payload livesExample
StoredSaved on your server, served to everyone who views itA comment, a profile name
ReflectedIn the request; the server echoes it into the responseA search term in an emailed link
DOM-basedNever in the server response; your client JS writes it into the DOMel.innerHTML = location.hash

In React. Text you render with {value} is escaped: it becomes text, never markup. OWASP: "Many frameworks escape every value they render by default… We recommend this approach." XSS gets in through the escape hatches, which the XSS Prevention Cheat Sheet lists:

  • dangerouslySetInnerHTML. React: "If the HTML inside isn't trusted (for example, if it's based on user data), you risk introducing an XSS vulnerability" (react.dev). Rendered markdown and rich text land here. Sanitize with a vetted HTML sanitizer (e.g. DOMPurify) first.
  • User URLs in href/src. javascript:… runs code when clicked. React 19 errors on javascript: URLs in src and href (upgrade guide changelog); earlier versions only warned. OWASP: this "does not replace application-specific URL validation". Allow https: only.
  • Anything outside React's rendering: ref.current.innerHTML, eval, a server template that builds HTML.

What the script can do once it runs (behaviour B): send any request as the user, with the cookie; read the page, including your CSRF token, so every CSRF defence is gone; read any token in localStorage or a non-HttpOnly cookie and take it away. HttpOnly changes only that last part: the attacker can use the session while the tab is open but can't take it. That's why it matters, and why it isn't enough.

Apply, 3 minutes. Review each line: safe or XSS, and what the attacker gets

(1) <p>{comment.body}</p>
(2) <div dangerouslySetInnerHTML={{ __html: marked(comment.body) }} /> (a markdown renderer that passes raw HTML through)
(3) <a href={user.website}>, where a user sets their website to javascript:fetch(…), on React 18
(4) A PR description: "Not a concern: the session cookie is HttpOnly, so XSS can't do anything with it."

(1) Safe. React escapes it, so <script> shows up as text.

(2) Stored XSS. The comment's <img onerror> becomes real markup for every reader. Sanitize the HTML before inserting it.

(3) XSS on click. React 18 only warns and renders the link; React 19 throws instead. On either, validate the scheme yourself (https: only).

(4) Wrong. The script calls fetch("/api/transfer", …) from inside the page: same-origin, cookie attached, CSRF token readable. HttpOnly only stops it from taking the ID elsewhere.

4 · CSP: a second layer for when XSS gets in

A Content Security Policy is a response header that tells the browser which scripts it may run. The strict policy OWASP recommends (CSP Cheat Sheet):

Content-Security-Policy: script-src 'nonce-{RANDOM}' 'strict-dynamic'; object-src 'none'; base-uri 'none'
PartWhat the browser does
'nonce-{RANDOM}'Runs only <script nonce="…"> tags whose nonce matches. The server generates a fresh one "for each HTTP response", so an attacker can't predict it. Injected inline scripts and inline handlers (onerror=, onclick=) are blocked.
'strict-dynamic'Scripts that a trusted script loads are trusted too, so your bundle can load its chunks.
object-src 'none', base-uri 'none'Close two older ways to load code (plugins, rewriting relative script URLs).

Use nonces or hashes, not a list of allowed domains: OWASP calls the strict form "more secure as it is less likely to be bypassed". And CSP "should not be relied upon as the only defensive mechanism against XSS": it limits what an injection can run, it doesn't fix the injection.

Apply, 2 minutes. With the strict CSP above, does it run?

(1) The stored comment <img src=x onerror="fetch(…)"> from §3, via dangerouslySetInnerHTML.
(2) An injected <script src="https://evil.com/x.js"></script>.
(3) A compromised npm package inside your own bundle.
(4) Your server adds the nonce with a middleware that stamps every <script> tag in the HTML it sends.

(1) Blocked. Inline event handlers don't run under a nonce policy.

(2) Blocked. The tag has no matching nonce.

(3) Runs. It's part of your script, which carries the nonce. CSP stops injected code, not code you shipped.

(4) Injected scripts run. The middleware stamps the attacker's tag too; OWASP warns against exactly this. Put the nonce in your templates, not on whatever HTML goes out.

Retrieval check · 5 minutes, cold, no scrolling

Without scrolling up

Say it out loud first, then write it. An interviewer asks: "Your app uses a session cookie. Walk me through XSS and CSRF: how each one attacks a logged-in user, and what you'd do about each." Cover: (1) the browser behaviour each attack relies on; (2) what each attacker can and can't do; (3) two CSRF defences, each with what it takes away from the attacker; (4) where XSS gets into a React app, and what CSP adds.

(1) CSRF: the browser attaches cookies by where a request goes, not who started it. XSS: any script in your page has your page's full powers.

(2) CSRF sends requests as the user but can't read responses, and only works against cookie auth. XSS can send any request and read everything, including CSRF tokens.

(3) Any two: SameSite=Lax/Strict (the cookie stays off cross-site requests; not across sibling subdomains, not on a GET link with Lax); a CSRF token (the attacker can't know a value the request needs); Fetch Metadata (the server rejects state-changing requests the browser marks cross-site); a required custom header (forces a preflight your CORS policy refuses). Plus: never change state on GET.

(4) Through escape hatches: dangerouslySetInnerHTML with unsanitized HTML, user URLs in href, direct DOM writes. A strict nonce CSP stops injected scripts and inline handlers from running, as a second layer, not a fix.

Sentence to have ready: "Both attacks use the fact that the browser holds the user's login. CSRF gets the browser to send a request from another site, and the cookie goes with it, so I set SameSite, never change state on GET, and check a CSRF token or Fetch Metadata on writes. XSS gets code into our page, where it can do anything the user can, including bypassing those CSRF defences. So the main defence is not having it: React escapes by default, and I treat dangerouslySetInnerHTML and user URLs as the risk points. A strict nonce CSP is the second layer, and HttpOnly means a successful XSS can use the session but can't take it."
