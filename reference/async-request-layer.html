The async request layer

Debounced query → cancellable request → results, error, loading. The whole thing, so that writing it costs no lookups.

Reference · Verified against MDN and the WHATWG DOM and Fetch standards, September 2026

From exercise 0004: you chose the right technique, and then the clock went on looking up AbortController. You don't need to understand anything new here. You need to be able to write it cold.

The whole layer

const [results, setResults] = useState<Book[]>([]);
const [error, setError]     = useState<string | null>(null);
const [loading, setLoading] = useState(false);

useEffect(() => {
  if (!debounced.trim()) {
    setResults([]); setError(null); setLoading(false);
    return;
  }

  const controller = new AbortController();   // one per run of the effect
  setError(null);                             // new query clears the old failure
  setLoading(true);

  search(debounced, controller.signal)        // signal goes INTO the call
    .then(setResults)
    .catch(() => {
      if (controller.signal.aborted) return;  // superseded, not failed: swallow
      setError("Search failed. Try again.");
    })
    .finally(() => {
      if (!controller.signal.aborted) setLoading(false);  // see trap 3
    });

  return () => controller.abort();            // abort() lives in the cleanup
}, [debounced]);

Where each piece goes

PieceWhereWhy there
new AbortController()Inside the effect body Each run needs its own. If you share one, an abort kills the next request too, and a signal can't be un-aborted.
controller.signalPassed as an argument to search() / fetch(url, { signal }) The call subscribes to it. If you create the signal but never pass it, nothing can be cancelled.
controller.abort()The cleanup function React runs the cleanup just before the next run of the effect and on unmount, which is exactly when a request becomes stale. This is the half you didn't wire in 0002.
signal.abortedInside .catch and .finally This is how the handlers tell "superseded" apart from "failed".

The traps

  1. try/catch around a promise you don't await catches nothing. search() returns straight away. The rejection happens later, after the try block has already exited. Use either .catch() on the chain, or await inside the try. (You closed this one in 0004. It's here for the record.)
  2. Aborting rejects the promise, so your .catch runs on every keystroke that supersedes a request. If you don't guard it, the user sees an error message for a request they never saw fail. Check controller.signal.aborted rather than err.name === "AbortError". The rejection value is the signal's reason, and that is only an AbortError when abort() is called without an argument. abort(reason) rejects with whatever you passed.
  3. The aborted request's .finally fires after the new request has started. Here is the order within a single commit: the cleanup aborts request A, then the new effect calls setLoading(true) for request B. A's rejection handlers are microtasks, so they run afterwards. If A's finally does setLoading(false) unconditionally, the spinner disappears while B is still in flight. The same guard fixes it.
  4. fetch doesn't reject on 404 or 500. It only rejects when the request itself fails: a network error, a bad URL, or an abort. For an HTTP error it resolves with res.ok === false, so you have to throw that yourself: if (!res.ok) throw new Error(`HTTP ${res.status}`). (The search() in the exercises rejects directly, so this trap only appears once you use real fetch.)
  5. The error has to clear when the next query starts, not when a request succeeds. Otherwise it sits on screen under the new results. Clear it in the effect body, next to setLoading(true).

Same layer with async/await

An effect can't be async itself, because its return value has to be the cleanup function and not a promise. So you define an async function inside it and call it.

useEffect(() => {
  if (!debounced.trim()) {
    setResults([]); setError(null); setLoading(false);
    return;                          // search("") matches everything
  }
  const controller = new AbortController();
  const { signal } = controller;

  async function run() {
    setError(null);
    setLoading(true);
    try {
      setResults(await search(debounced, signal));   // await INSIDE the try
    } catch {
      if (!signal.aborted) setError("Search failed. Try again.");
    } finally {
      if (!signal.aborted) setLoading(false);
    }
  }

  run();
  return () => controller.abort();
}, [debounced]);

Facts, if asked

QuestionAnswer
Calling abort() twice, or after the request finished? No-op. The first step of the spec's algorithm is "if signal is aborted, return". Once the promise has fulfilled, rejecting it does nothing. So an unconditional abort in the cleanup is safe.
What does abort() with no argument reject with? A new DOMException named "AbortError".
Abort after the headers have arrived but while the body is still being read? The body stream errors, so res.json() rejects with the same reason. One abort covers the whole request.
Timeout? AbortSignal.timeout(ms) rejects with "TimeoutError", not "AbortError". That is deliberate: you should show a timeout to the user and swallow a cancel.
Timeout and cancellation together? AbortSignal.any([controller.signal, AbortSignal.timeout(5000)])
Can you skip AbortController and use a boolean instead? Yes, and it fixes what gets rendered. react.dev's own example uses an ignore flag set in the cleanup. It doesn't cancel the request, though: the response still downloads and your server still does the work. Say that trade-off out loud.

Sentence to have ready: "Each run of the effect owns a controller. The cleanup aborts it, so a superseded request can't overwrite newer results. Its rejection gets swallowed rather than shown, and its finally doesn't touch the loading flag, because by then a newer request owns that flag."
