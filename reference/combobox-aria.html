Combobox ARIA

Which element carries which attribute, and the one rule that decides it. Roving tabindex is at the end for contrast.

Reference · Verified against the W3C ARIA Authoring Practices Guide (APG), September 2026

In 0003 you picked aria-activedescendant for the right reason and put it on the <ul>. In the sheet 1 rewrite you created the AbortController where the cleanup couldn't reach it. Both times you remembered the technique and got its placement wrong. This sheet is about placement.

The rule

aria-activedescendant goes on whichever element has DOM focus. Assistive tech reads it from the focused element and treats the element it points to as focused. When it sits on any other element, nothing reads it.

In a combobox the input has DOM focus the whole time, because the user is typing. So the input carries aria-activedescendant, and the list only holds the ids it points to. Nearly every other attribute follows from this.

Placement

ElementCarriesNote
<input> role="combobox"The whole widget is named after the input, not after the list.
aria-expandedtrue when the list is visible. Default is false.
aria-controls="<list id>"Points at the popup. APG: only needed while it's visible.
aria-activedescendant="<option id>"The active option's id. Remove it when nothing is active.
aria-autocomplete="list"list means the suggestions filter as the user types. both adds inline completion text.
a labelA <label> if there's a visible label, otherwise aria-label. A placeholder is not a label.
<ul> role="listbox"Needs no name of its own when it's part of a combobox.
idThe target of the input's aria-controls. Nothing else goes here: not aria-activedescendant, not tabindex.
<li> role="option"Without it, listbox has no children it recognises.
idUnique. This is what aria-activedescendant points to. Build it with useId().
aria-selected="true"On the active option. In a combobox, selection follows focus.

Not needed: aria-haspopup, because combobox already implies listbox (you only set it for a grid, tree or dialog popup). Also not needed: aria-owns on the input. That was how ARIA 1.0 did it, and the APG says to use aria-controls instead.

Traps

  1. aria-activedescendant on the listbox. It's valid ARIA, since listbox supports the attribute, so no linter will complain. But the listbox never has focus, so nothing reads it. This is the 0003 miss.
  2. The id has to be inside the listbox. The APG's DOM rule: an element with role combobox may point aria-activedescendant at an element that is inside the element its aria-controls names. So if aria-controls is missing or points somewhere else, the reference is invalid.
  3. The active id must go away when the option does. If a new result set arrives and active keeps an old index, it now points at a different book or at nothing. (This is the stale-index miss from 0003 requirement 5.)
  4. aria-controls pointing at an unmounted list. If the <ul> only renders while the list is open, the id doesn't exist the rest of the time. Either set aria-controls only while the list is rendered, or keep the <ul> mounted and hide it. The 0004 scaffold gets this wrong.
  5. Scrolling is your job. DOM focus never moves, so the browser won't scroll the active option into view. The APG requires you to do it: scrollIntoView({ block: "nearest" }).
  6. A mouse click must not take focus away from the input. Call preventDefault() on the option's mousedown. Otherwise the input blurs before the click event fires.

The contrast: roving tabindex

This one is for widgets where real focus can move, because the user isn't typing into anything: tabs, toolbars, menus, radio groups. The APG's own toolbar and tabs examples use it.

ElementCarries
ContainerThe role (tablist, toolbar, menu, radiogroup). No tabindex.
The one current itemtabindex="0". This is the group's single stop in the Tab order.
Every other itemtabindex="-1". They can be focused from script but are skipped by Tab.
On an arrow keyMove the 0 to the next item, then call .focus() on it. This needs a ref for each item.
Questionaria-activedescendantRoving tabindex
