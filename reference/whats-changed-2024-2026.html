The rendering strategies, disambiguated

This is the Q4 material, and it's the one most likely to be probed, because conflating RSC with SSR is the single most common tell that someone read the headlines rather than the docs.

Server-side rendering		 Server, then browserYes Yes. HTML arrives first, then the same component's JS boots and attaches

RSC
React Server Components		 Server only No. This is the whole point No. Emits a serialised payload the client renders into the tree

The sentence to have ready: "SSR renders on the server and then hydrates the same component on the client, so you pay for the JS twice. A Server Component runs only on the server and never hydrates — its dependencies never reach the browser at all. They compose: a Server Component can render a Client Component, not the other way round."

The follow-up you should expect: "So when would you not use RSC?" Good answers: anything needing interactivity, state, effects or browser APIs must be a Client Component; RSC adds a server you now have to run and pay for; and a heavily interactive app may get little benefit while inheriting real architectural complexity. Naming the cost unprompted is the staff-level move.

The memoisation shift

In 2024, knowing when to reach for useCallback was a senior skill. Since Compiler 1.0 it largely isn't — the compiler inserts memoisation across the tree automatically. What did not get automated:

  • Structural problems. Mounting 10,000 DOM nodes is still wrong; virtualise it.
  • State architecture. A context holding one fat object still re-renders every consumer.
  • Network waterfalls. Sequential dependent fetches are still the most common real cause of a slow page.
  • Bundle size. The compiler doesn't delete the 300 kB date library.

So the interview question shifted from "how do you optimise a React component?" to "how do you find out what's actually slow?" — profile first, name the layer, then fix the layer. Reaching for React knobs before measuring is now the wrong-sounding answer.

Cumulative Layout Shift		 Visual stability — unexpected movement≤ 0.1

Why the FID → INP swap matters for a React candidate. FID only measured the delay before the first interaction's handler began — trivially good on most apps, and easy to game. INP measures the full latency from interaction to the resulting paint, across every interaction in the session. That makes it the metric that punishes excessive re-rendering, which puts it directly downstream of everything in lesson 2. Connecting those two out loud is a strong performance answer. web.dev — INP
